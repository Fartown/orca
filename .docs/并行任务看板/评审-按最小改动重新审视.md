# 评审 · 按「最小改动」重新审视

评审轴（用户 2026-08-27 给定）：

1. 相对 **main 分支**尽量少改动；
2. 不动原有的 Workspaces 功能；
3. Issues 尽量复用 Workspaces 已有的能力；
4. 在此基础上尽量少和主干冲突。

本文用这四条重新审视现有实现与方案，结论与之前基于「问题现象」的方案不同。

## 1. 冲突面：实测不大，不是主要矛盾

相对 main 改动的既有文件共 25 个。按主干近 400 次提交的改动频次排：

| 文件 | 主干改动次数 | Issues 的改动 |
| --- | --- | --- |
| `src/main/index.ts` | **23** | +27 行，纯新增注册 |
| `src/main/orcad/orcad-entry.ts` | **8** | +26 行，纯新增注册 |
| `src/shared/protocol-version.ts` | 5 | +3 行，一个 capability 常量 |
| `src/main/runtime/rpc/methods/index.ts` | 1 | +2 行，一个 import 与 spread |
| 其余 21 个 | **0** | 多为 ≤4 行 |

结论：**冲突面已经控制得不错**，热点只有两个且都是加法。这一条不需要大动。

## 2. 改动面：8393 行里最大的一块是重复的

| **会话身份 / 运行附件 / 分配 / hook 摄取** | **2210** | **与 Orca 已有的 `AiVaultSession` 大量重叠** |

## 3. 逐项对照：Issues 自建了什么，Orca 已经有什么

`AiVaultSession`（`shared/ai-vault-types.ts:83`）的现成字段：

| Issues 自己存的 | Orca 已有的等价物 | 来源 |
| --- | --- | --- |
| `conversations.agent` | `AiVaultSession.agent` | transcript 扫描 |
| `conversation_provider_identities.session_id` | `AiVaultSession.sessionId` | transcript 扫描 |
| `conversation_provider_identities.transcript_path` | `AiVaultSession.filePath` | transcript 扫描 |
| `conversations.title` | `AiVaultSession.title` | `custom-title` → `ai-title` → 首条用户消息 |
| `conversations.workspace_*_snapshot` | `AiVaultSession.cwd` / `branch` / `executionHostId` | transcript 扫描 |
| `conversations.created_at` / `updated_at` | `AiVaultSession.createdAt` / `updatedAt` / `modifiedAt` | transcript 扫描 |
| `ConversationRuntimeAttachmentRegistry` | agent-status store + `sleepingAgentSessionsByPaneKey` | 与 Workspaces 同源 |
| `conversations.execution_state` | agent-status store 的实时状态 | 与 Workspaces 同源 |

**关键差别在数据来源**：Orca 从 transcript（权威、可重扫、自愈）算，Issues 从 hook 事件流（一次性、有损、易错判）推。
问题 1、6、8、9、10、14 全部落在这一层——**它们不是六个独立的 bug，是同一个选择的六个表现**。

反例佐证：`transcript_path` 这一列，Orca 那边叫 `filePath`，一直是对的；Issues 自己存的那份被
无条件覆盖成 `null` 且不可恢复（问题 8）。

## 4. Issues 真正必须自己持久化的东西

按「复用优先」重新划线，只有三样是 Orca 没有、必须新建的：

| 必须新建 | 为什么 Orca 没有 | 规模 |
| --- | --- | --- |
| Issue 树（本地 Issue、层级、归档、外部引用快照） | Orca 无此概念 | 953 行，已有且合理 |
| **绑定**：`sessionId → issueId` | Orca 无此概念 | 一张两列表 |
| **已读 / 已处理**：哪一轮还需要我 | Activity 的 ack 是 pane 级、语义不同 | 需要，但只需存用户状态，不需存轮次全文 |

其余的「会话是什么、叫什么、在哪个工作区、是否在跑」——**Orca 全都已经算好了**。

## 5. 两个方案

### 方案 A · 保持现状，逐个修 15 项

- 相对 main 的改动面：不变（8393 + 2199 行）
- 冲突面：不变（已经不大）
- 工作量：6–8 处修改
- 遗留风险：2210 行的重叠层继续与 ai-vault 各算各的。**今后 Orca 改动 transcript 解析、标题优先级、
  session 身份语义时，两边会持续漂移**，而漂移不会报错，只会表现成「Issues 里的名字/状态和右侧
  Session History 对不上」。

### 方案 B · 会话层改为投影，只保留三样自有事实

会话侧读路径改为：**`AiVaultSession`（身份、标题、工作区、transcript）⊕ agent-status store（实时状态、pane）
⊕ 绑定表（issueId）⊕ 已读表**。这正是 Workspaces 的做法，只是多了 Issue 这一维分组。

- 相对 main 的改动面：**可删除约 2210 行重叠层**，连带 DB/schema/收据/投影按比例缩减
- 冲突面：不增加（删除的都是新增文件，不碰既有文件）
- 一次性消除：问题 **1、6、8、9、10、14**（它们全在这一层）
- 不动：Issue 树、层级、RPC 协议、Workspaces
- 工作量：重做会话侧读路径与投影
- **必须如实说明的代价**：
  - `AI_VAULT_AGENTS` 只覆盖 17 个 agent，而 `TuiAgent` 有 36 个。对那 19 个没有 transcript
    解析器的 agent，Issues 将不再有持久会话记录——但 Orca 的 Session History 本来也没有，
    所以结果是**与 Orca 一致**，而不是更差；
  - ai-vault 是扫描式，实时性不如 hook。实时状态必须继续由 agent-status store 提供
    （这本来就是 Workspaces 的做法，不是新增依赖）；
  - 轮次记录（1518 行）不能整体删除——「需要我」需要持久的已读/已处理状态。但**轮次全文预览
    可以改为按需从 transcript 读**，只持久化用户状态。

## 6. 建议

按用户给定的评审轴，**方案 B 才是「相对 main 尽量少改动」的答案**——它让最终 diff 变小，而不是变大。

但方案 B 是结构性的，不宜和止血混在一起。建议分两步：

1. **立即**：修问题 8（`transcript_path` 被覆盖，一行）与问题 14（死分支，一行）。
   两者独立于任何结构选择，且问题 8 每天都在丢不可恢复的数据。
2. **然后**：决定 A 还是 B。若选 B，问题 1、6、9、10 不必单独修——它们随重叠层一起消失；
   届时只需再单独处理问题 4（点不开）、12（收据）、13（死字段）。

若选 A，则按 [`改动方案-六个问题.md`](./改动方案-六个问题.md) 的 WP-A/B/C 执行。
