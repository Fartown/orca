# 总管第一版：建在「任务为主的工作流」上的接口方案

状态：草案，待用户确认 D-012～D-016（见 journal）。

依据：

- [Fartown/orca#81](https://github.com/Fartown/orca/pull/81)：本地任务「任务为主的工作流」，分支 `feat/local-tasks-task-first-design`。下文「PR #81」指其中的产品方案、需求 REQ-022～REQ-030、技术方案 M1～M14。
- 本功能的 [总体方案](超级智能体总体方案.md) 与 [技术方案](超级智能体技术方案.md)。

## 0. 结论

PR #81 已经把总管需要的大半零件设计好了：

- **任务成为记录**：每个会话属于一个任务，进展、轮次结束、派活、验收都落在任务时间线上。
- **调度会话**（REQ-030、M13）：理解请求，只读查询，要新建东西时用 `orca task propose` 交结构化提案，用户确认后由 Orca 执行。
- **回写进展**（REQ-022、M2）：会话每轮结束用 `orca task progress` 写三段式结果；没写时有「轮次结束」记录兜底。
- **需要你**与**待验收**：会话在等你、任务在等你，都已是确定的判定。

所以第一版的总管 = **把 PR #81 的调度会话升格为常驻、唯一的总管**：

- **任务就是总管的账本**：不另建事项表，总体方案里的「事项」在第一版就是本地任务。
- **会话照 PR #81 从任务启动**；总管自己不动手，只经提案分配和驱动。
- **感知靠 PR #81 已有的记录**，只补一个「收件箱 + 空闲时唤醒」，让总管在它关心的任务有变化时被叫醒。

第一版只做**分配、管理、感知**三件事；定时复查、观察器、对外动作（飞书、合 PR）、委托、探查员放到后面。

## 1. 与 PR #81 的对齐

| PR #81 的约定                                                  | 总管第一版怎么做                                                                          |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 原则 2：人说了才开工，不因状态变化、定时、主机恢复而自动开会话 | 总管被唤醒后只能**汇报和提案**；新建任务、开会话、追加指令都走提案，用户确认后由 M11 执行 |
| 原则 5：完成由人定，CLI 写入不能进已完成类别                   | 总管的写入来源也是 `cli`（`M/local-tasks/local-tasks-rpc-caller.ts:7`），同样标不了完成   |
| 原则 6：不轮询、不重试、不排队                                 | 感知用推送；主机不在联系就返回「无法确认」                                                |
| 调度会话在桌面浮动伪工作区里，手机经配对桌面                   | 总管同样在这里，同一 profile 只有一个                                                     |
| 提案确认后由客户端执行，主机不代为执行（M13）                  | 照此；提案就是总管的「审批」                                                              |
| 「直接执行」设置（提案提交后不等确认）                         | 沿用；默认关                                                                              |

**建议 PR #81 改的三处**：

1. **调度会话用终端启动（Claude）**。M13 用 `launchAgentInNewTab`，走结构化聊天还是终端取决于用户设置（`S/structured-native-chat-launch-route.ts:58` 的 `nativeChatPreferenceFor`）。Claude 的结构化聊天经 Claude Agent SDK，Anthropic 不允许第三方产品用它跑 claude.ai 订阅（本功能 D-007）。
   - 所以 Claude 总管固定以终端启动，对话页照样嵌 `NativeChatView`：它本来就接受终端标签（`terminalTabId`、`paneKey`）。
   - Codex 可以保留结构化（`codex app-server` 是 OpenAI 官方接口）。
2. **对话标识不用 `ORCA_AGENT_SESSION_ID`**。这个变量只注入结构化会话（`M/runtime/structured-session-child-env.ts:69`），终端里没有。改为 CLI 传 `ORCA_PANE_KEY`，主机按「启动调度会话时记下的面板」映射到对话行。结构化会话同样有面板标识，两种形态走同一条路。
3. **提案不只是「建任务并开会话」**。把总管所有会写入的意图都放进同一种可确认的提案，由 M11 用现有函数逐项执行（§2.4）。

## 2. 接口

### 2.1 原则

- **唯一入口是 `orca` CLI**，输出 `--json`，正文用 `--body` / `--body-file`，报错写给智能体看（沿用 PR #81 M3 的约定）。不另做 MCP。
- **读不需要确认；凡是新建或驱动，都走提案**。用户打开「直接执行」时，提案提交即执行。
- **只读记录，不读过程**：总管看任务、进展、状态与判定，不翻会话的终端内容。这既省 token，也避免「会话说了什么」与「任务记的是什么」对不上。
- **按主机联系判定**：每次读写都按任务库或会话所在主机的联系状态执行；不在联系就返回 `unverifiable` 与原因，不重试。

### 2.3 会话

会话不单独开一套接口，一律**挂在任务上**来看、来管，复用 PR #81 与 Orca 现有的。

| 要做的事           | 用什么                                                                                                                    | 说明                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 看会话             | `task show --json` 的会话段：智能体、终端或聊天、状态、判定（`live` / `unverifiable` / `exited`）、最后一句话、在等你什么 | 数据来自任务关联与主机的智能体状态（已有）                                 |
| 看没挂任务的会话   | `orca worktree ps --json`（已有）                                                                                         | 用于提一个「记成任务」的提案                                               |
| 诊断时看一眼终端   | `orca terminal read --tail 30`（已有）                                                                                    | 只在用户问「卡在哪」时用，限行数                                           |
| 开会话、建子任务   | 提案项 `start`、`subtask`                                                                                                 | 执行走 M11 → `agent.launch`；从任务启动的会话按 PR #81 附任务说明          |
| 给会话追加一句指令 | 提案项 `append`                                                                                                           | 执行走 M11 的追加路径：只发给「做完一轮」的会话（REQ-015），正在工作的不发 |
| 停会话             | 提案项 `stop`                                                                                                             | 破坏性，总是要确认（「直接执行」也不跳过）                                 |
| 替用户批准、回答   | **不提供**                                                                                                                | 会话在等你批准或回答时，由用户在速览里处理（PR #81 §5.4）                  |

### 2.4 提案项

在 PR #81 M13 的 `LocalTasksProposalItem` 上加一个 `kind`，旧提案（没有 `kind`）按 `start` 处理：

```ts
// S/local-tasks/local-tasks-rpc-params.ts（3c）
export const LocalTasksProposalItem = z.discriminatedUnion('kind', [
  z.object({ kind: z.literal('start'), title, target, agent, prompt }), // PR #81 原有：建任务、绑定、开会话
  z.object({ kind: z.literal('subtask'), parentTaskId: id, title, agent, prompt }), // 在任务下建子任务并开会话，同一工作区
  z.object({ kind: z.literal('append'), taskId: id, sessionLinkId: id, text: prompt }), // 发给做完一轮的会话
  z.object({ kind: z.literal('stop'), taskId: id, sessionLinkId: id, reason: z.string().max(500) }),
  z.object({ kind: z.literal('link'), taskId: id, target: worktreeTarget }), // 把已有工作区挂到任务（「记成任务」时用）
  z.object({ kind: z.literal('record'), title, target: worktreeTarget }) // 把没挂任务的会话记成任务
])
```

- 每一项在提案卡上单独显示，可以改、可以去掉（PR #81 原有）。
- `stop` 永远要确认；其他项在「直接执行」打开时可以不等确认。
- 执行时逐项调用现有函数：
  - `start`、`subtask` → `local-task-dispatch-launch.ts`；
  - `append` → `sendLocalTaskReply`；
  - `stop` → 关标签或 `terminal.close` / `agentSession.close`；
  - `link` → `links.linkWorkspace`；
  - `record` → `tasks.create` + `links.linkWorkspace`。
- 每项执行的结果写回提案行，并在对应任务的时间线上记一条「由总管提案、你确认」。

### 2.5 感知：收件箱与唤醒

**总管关心哪些任务（盯着的任务）**：

- 由它的提案建出的任务，确认执行后自动加入；
- 用户说「帮我盯着 ORC-39」时，总管用 `task watch ORC-39` 加入；
- 任务收尾（完成或取消）后自动移出。

**收件箱里有什么**（只有确定的事实，不推断）：

| 事件                     | 来源                                          |
| ------------------------ | --------------------------------------------- |
| 智能体回写了进展         | PR #81 M2：带 progress 标记的评论             |
| 会话做完一轮             | PR #81 M2：`turn-ended` 记录                  |
| 状态变化（含进入待验收） | 现有的状态事件；评审类别即待验收（PR #81 Q3） |
| 会话在等你 / 不再等你    | 现有的需要你判定（REQ-014），按判定键去重     |
| 会话结束                 | 现有的会话关联与主机判定                      |
| 提案被确认或去掉         | PR #81 M13 的提案表                           |
| 主机失联 / 恢复联系      | 桌面的主机联系状态                            |

**数据与接口**：

- 不新增事件表：收件箱是「盯着的任务」上 `events.id > 游标` 的事件，加上需要你判定的变化。
- 两张小表，与 PR #81 v6 的对话表同一次升级：
  - `local_task_conversation_watches(conversation_id, task_id, added_at, added_by)`；
  - `local_task_conversations` 加 `inbox_cursor` 列。
- RPC（由各任务库所在主机提供）：
  - `localTasks.dispatcher.inbox { conversationId, cursor?, limit }` → `{ items: [{ at, taskRef, kind, summary, sessionLinkId?, needsYou? }], cursor }`；
  - `localTasks.dispatcher.watch` / `unwatch { conversationId, taskId }`。
- 任务在 orcad 主机或配对服务器的库里时，那台库只存桌面的对话 id（PR #81 已这样约定）。
- `task inbox` 在桌面按「在联系的库」逐个读、合并、按时间排序；不在联系的库在结果里标「无法确认」。

**唤醒**（放在 PR #81 M13 的 `R/local-tasks/local-task-dispatcher-session.ts`）：

- 桌面渲染层本来就订阅各库的 `localTasks.subscribeChanges`。盯着的任务有变化时：
  1. 计算总管的未读数；
  2. 2 秒内合并成一批；
  3. **只在总管会话是「做完一轮」（空闲）时**，经会话自己的输入通道写入一行指针，例如「有 3 条任务动态：ORC-39 回写了进展，ORC-41 待验收。运行 `orca task inbox --json`」。终端会话用现有的终端发送，结构化会话用 `agentSession.send`。
- 每个空闲期最多唤醒一次；总管在工作、等批准、等回答时不写；读完 `--ack` 后才推进游标。
- 设置：「有动态时叫醒总管」开 / 关，默认开，只针对盯着的任务。
- 用户正在总管的输入框里打字时不写（聊天视图的输入框状态可知；终端焦点下的半行输入不可知，V-c）。

**为什么不用编排的收件箱**：编排的指针投递（只在空闲时、最多一次）正是这个语义。但 PR #81 整条工作流不经编排，总管也不是编排协调者；为了唤醒多建一个 Run、多依赖一套上游模块，不值得。这里用同样的语义在本功能里实现，约一个模块。

**主动通知用户**：

- 确定性的提醒 PR #81 已有：首页「需要你」与待验收，桌面与手机都显示。
- 总管只补「需要判断的」：被唤醒后在对话里用一两句话汇总，必要时附一份提案，例如「ORC-39 已定位到重连逻辑，下一步写复现测试；要我让它继续吗？」，下面是 `append` 提案卡。
- 总管这一轮说完时，现有的「智能体做完一轮」通知照常触发（它本身就是一个智能体会话），手机推送随之到达。

## 3. 典型流程

1. **派活**：「看看 orca 里哪些工作区的 PR 还没合，各开一个任务跟进」。
   - 总管用现有只读命令查工作区与 PR 状态（同 PR #81 §6.4 的例子）；
   - 交一份 3 个 `start` 项的提案；你去掉一项后确认；
   - M11 建任务、绑定、开会话，这两个任务自动加入「盯着的任务」。
2. **感知**：半小时后，ORC-39 的会话 `task progress` 回写一条；ORC-40 的会话进入等你批准。
   - 总管空闲 → 收到指针 → `task inbox`；
   - 它对你说「ORC-39：已定位到重连逻辑，下一步写复现测试。ORC-40 在等你批准（点速览）」，并附一张 `append` 提案：「让 ORC-39 继续写复现测试」。
3. **管理**：你说「ORC-40 换成 codex 重来」→ 一份提案：`stop` ORC-40 的 claude 会话，再加一项 `subtask`（codex，同一工作区）。
4. **一天后问**：「ORC-39 做到哪了」→ `task show ORC-39 --json`，按最新进展与状态回答，并写明记录的时间；不靠对话记忆，总管被压缩、重启过也一样。
5. **SSH**：ORC-41 的工作区在 minizc（orcad），任务在 minizc 的库里。
   - 总管读写都带 `--host`；
   - minizc 失联时，`task list --all-hosts` 把它标「无法确认」，收件箱暂时读不到那台库，恢复联系后由那次联系触发重读一次。

## 4. 总管的工作说明（`task guide --dispatcher` 的要点）

1. 你是用户在 Orca 里的总管：理解、分配、跟进、汇报；不自己写代码，不在工作区里动手。
2. 被问到任务和进度，先查记录（`task list` / `task show` / `task inbox`），不凭对话记忆；回答时写明记录时间。
3. 新建与驱动一律 `task propose`；一份提案尽量把一件事要做的几步放在一起。
4. 只读命令可以直接用；不读会话的终端过程，除非用户问「卡在哪」，最多读 30 行。
5. 完成由人点；你最多把任务推进到待验收。
6. `unverifiable` 不是失败也不是结束；主机连不上时如实说，不要重试。
7. 被唤醒后：先 `task inbox --json`，只汇报需要用户知道或决定的；没有就一句话或不说；最后 `--ack`。
8. 不等待、不 sleep、不轮询；没有事就结束本轮。

## 5. 与本功能总体方案的对应

| 总体方案                       | 第一版（在 PR #81 上）                                                                             |
| ------------------------------ | -------------------------------------------------------------------------------------------------- |
| 事项 `S-n`、总管账本           | 本地任务 + 动态 + 提案表 + 对话表 + 盯着的任务                                                     |
| 完成条件由内核核对             | 完成由人点（PR #81 原则 5），比完成条件更严                                                        |
| 看门狗「无人跟进」             | 第一版只覆盖盯着的任务：进行中却没有会话、也没有进展超过阈值时，作为一条收件箱事件给总管（后续）   |
| 唤醒：编排收件箱               | 本功能的收件箱 + 空闲时一行指针                                                                    |
| 派工：`orca super dispatch`    | 提案 `start` / `subtask` → M11 → `agent.launch`                                                    |
| 回执：`worker_done` + 事实核对 | `task progress` 三段式 + 轮次结束；提交与 PR 的核对后续                                            |
