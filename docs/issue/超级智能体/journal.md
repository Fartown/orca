### D-010 分工的线画在哪里

- 日期：2026-11-04
- 背景：用户要求总管既不能老是自己干，也不能芝麻小事都派 worker。方案 3.5 用四问判定（会改工作区、超过 30 秒、超过一屏、需要某台主机的环境），并配了代码层的硬约束和每日统计。争议点是「一行 typo」这类很小但会改文件的事。
- 最终决定：待用户确认。推荐第一项。
- 原因：线画在「改不改东西」上而不是「大不大」上，判据清楚、可由权限配置强制；改动都发生在 worker 的工作区里，有事项、有提交、可追溯。代价是一行小改也要开一个 worker，用「同一事项发给原 worker」与短命 worker 统计控制开销。
- 影响范围：REQ-2319；方案 3.5、4.12、5.3；走查 §8。

#### 备选项

- 凡改工作区一律派 worker；总管只做 Orca 记录与只读探查；阈值 30 秒、8 KB、短命 2 分钟（推荐）
- 允许总管直接改「单文件、少于 N 行」的小改，记入事项

### D-008 飞书对外发送用谁的身份

- 日期：2026-11-04
- 背景：用户的典型任务要求总管用飞书催人 review、在群里通知。发送由内核调用总管所在机上的 `lark-cli`。`lark-cli` 可以用本人身份，也可以用自建应用的机器人身份。
- 最终决定：待用户确认。推荐第一项。
- 原因：催 review 这类私聊用本人身份更自然，对方也更容易响应；每条消息都在委托内、逐条记回执。若团队不希望机器代发本人消息，改用机器人身份，并在消息里写明是自动发送。
- 影响范围：REQ-2318；方案 §4.11；V-8。

#### 备选项

- 本人身份（总管所在机上用户自己登录的 `lark-cli`）（推荐）
- 机器人身份（自建飞书应用），消息标明自动发送

#### 关联文档与需求点

- 无

### D-009 PR 合入默认由谁执行

- 日期：2026-11-04
- 背景：用户描述「点了 approve 后得手动合入，然后通知」。可以由总管在委托内合入，也可以只提醒用户去点合入。
- 最终决定：待用户确认。推荐第一项，并在每个交付 PR 事项的委托卡片上可改。
- 原因：合入前内核会核对评审结论、检查和有无新提交，比人手点更不容易漏；不放心的仓库在委托里改成「提醒我合」，完成条件同样是观察器看到 `merged`。
- 影响范围：REQ-2316、REQ-2318；方案 §4.10。

#### 备选项

- 总管在委托内合入，合入前由内核核对（推荐）
- 只提醒用户合入，观察器看到 merged 后发通知

### D-007 总管会话用官方 CLI 的交互式终端，不经 Claude Agent SDK

- 日期：2026-11-04
- 背景：初稿让 Claude 总管走 Orca 的「结构化会话」，那条路径经 Claude Agent SDK 启动。用户指出这样无法使用官方订阅。核实 Anthropic 文档：未经事先批准，第三方开发者不能让基于 Agent SDK 的产品使用 claude.ai 登录或订阅额度，应改用 API Key；Claude Code 的法律与合规页说明 Pro/Max 额度按普通个人使用估算。同时确认 Orca 已有终端会话的聊天视图（桌面与手机），编排的终端道唤醒支持终端里的协调者。
- 最终决定：采用第一项。总管是官方 `claude` / `codex` 在总管工作区里的交互式终端会话，用用户自己的登录；桌面与手机用终端聊天视图显示；唤醒走编排终端道。第一期 Codex 也走终端会话，保持一条路径。
- 原因：这就是用户自己在用 Claude Code / Codex，订阅可用；Orca 不经手凭据；聊天视图与唤醒都已有。用量随唤醒次数增长，靠事件驱动、条件复查与合并压低；高频场景由用户在 CLI 里自行改用 API Key。
- 影响范围：REQ-2301；方案 §1、§2、§3.1～§3.3、§6、§10、§11（新增 R-6、V-5）；D-001、D-006 的表述。

#### 备选项

- 官方 CLI 的交互式终端会话 + 终端聊天视图（采纳）
- 维持 Claude 结构化会话（Agent SDK），要求用户为总管配置 API Key

### D-001 总管本体：智能体 CLI 会话，还是 Orca 内置的模型循环

- 日期：2026-11-04
- 背景：Muse、Dots、Cue 是厂商托管的智能体，自带模型调用、凭据与沙箱；DeepSeek Super-agent 和 agent-autoloop 则把现成的命令行智能体当作路由与执行者。Orca 目前不直接调用任何大模型 API，凭据都是各 CLI 自己的登录；结构化会话、手机聊天、编排唤醒都已围绕 CLI 会话建好。
- 最终决定：待用户确认。推荐第一项。
- 原因：复用 Claude Code / Codex 的能力、登录与用量；手机现在就能和它聊天；编排的协调者、唤醒、问答直接可用；Orca 不新增模型凭据与计费面。代价是总管的行为受所选 CLI 的上下文与压缩影响，用账本与记忆兜底。
- 影响范围：REQ-2301、REQ-2303；方案 §0、§3。

#### 备选项

- 总管是用户选定的官方智能体 CLI 的交互式会话，作为编排协调者（推荐；形态见 D-007）
- Orca 内置模型调用循环与工具调用，自管 API Key

#### 关联文档与需求点

- 无

### D-002 总管所在机：桌面，还是常开的服务器

- 日期：2026-11-04
- 背景：总管需要看到所有主机。桌面 Orca 持有 SSH 连接与配对服务器，看得最全；但桌面合盖、关机时总管就不在线。常开的 `orca serve` 主机能 24 小时在线，但要由它持有对其他主机的连接。
- 最终决定：待用户确认。推荐第一项，并把「搬到常开主机」放进切片 5。
- 原因：第一期最少改动、最符合现有连接归属；离线时如实显示「总管不在线」，在主机上按时干活的事交给自动化（不依赖桌面开着）。
- 影响范围：REQ-2301、REQ-2306、REQ-2312；方案 §7、§10。

#### 备选项

- 第一期固定在桌面 Orca，之后支持迁到常开主机（推荐）
- 第一期就要求一台常开的 `orca serve` 主机

### D-004 动作默认级别
