# 会话命名与身份保护

## 1. 背景与目标

同一个 Agent 会话，无论从哪里查看，都使用一致、可辨认的名字；Provider 原生名可用时始终优先，后台调用不能顶替主会话的身份和名字。

本需求独立于 Issues。Issues 与 Workspace、Tab、Dashboard、History、Activity、通知一样，只是公共会话名称的消费者；有没有 Issue、是否启用 Issues，不改变命名规则。

本文是需求事实入口，不是新的技术方案。原 REQ-025/026/028 从 Issues 迁入，保留编号供已有方案、测试和历史证据追踪。`ready` 只表示需求已整理，不代表产品全部验收完成。

## 2. 已确认来源与范围

用户已明确确认：Provider 名第一；没有时保留回退名称；稳定提示词派生名排在实时标题前；左侧、顶部、仪表盘、通知等保持一致；Issues 不单独维护命名逻辑和存储；人工改名主要在 Provider 完成；修复后台调用/subagent 导致的主会话串名。

范围内：公共命名优先级、Provider 名读取及更新、各消费入口的一致性、主会话身份不被后台调用顶替、已有数据的兼容。

范围外：新建人工改名系统、人工名数据库或编辑 RPC、批量迁移或删除旧数据、额外命名 LLM、重写会话管理或 Issues 的组织/绑定/恢复业务。普通 shell 的终端标签不强制按 Agent 会话规则改写。

## 3. 需求点

### REQ-025 统一会话名称与优先级

优先级：P0。当前状态：实现及验收进行中，不能以历史局部测试代替全入口验收。

统一排序：**Provider 原生名 → 已有 Orca 会话人工名 → 有效、稳定的提示词派生名 → 可信终端实时标题 → 有明确归属的已有标签 → 默认兜底。**

- 有 Provider 原生名时，各入口都使用它；Provider 改名后，对应会话的显示随之更新。
- 已有 Orca 人工名只作为兼容回退，不新建人工改名能力。
- 派生名取首次有效任务摘要；“继续”“好的”等无任务内容的输入不抢占名称。已有有效摘要不随每轮状态或实时标题变化而跳动。
- 读取暂时失败不等于名字被撤销，不因此丢掉同一会话已确认的原生名。
- Workspace 左侧、顶部 Tab、Issues、Dashboard、History、Activity、通知及其他会话选择入口使用同一规则；任务预览和状态可以独立显示，不能替换会话主名。
- 分屏各 pane 使用各自会话的名字，顶部显示当前活跃 pane 的结果；名称不参与身份匹配。

验收：有原生名、无原生名逐层回退、原生改名三类场景中，同身份在各入口显示一致；状态变化和后续“继续”不让稳定名称跳动。

### REQ-026 公共归属与已有数据兼容

优先级：P0。当前状态：实现及验收进行中。

- 读取、排序、缓存和投影归公共会话命名能力，不归 Issues。
- Issues 只消费公共结果。绑定、改绑、解绑和切换筛选条件不改变会话自己的名字。
- 没有 Issue 或 Conversation 记录时，公共自动命名仍能工作。
- 已有人工名、旧列和旧端行为保留兼容；不借本次修复新增数据库、编辑 RPC、迁移账本或批量删列。

验收：停用 Issues 业务装配时，Workspace、Tab 等仍可正常命名；Issues 组织操作不创建另一套名称来源。旧数据兼容用例继续保留，不将兼容现状写成新产品目标。

### REQ-028 主会话不被后台调用顶替

优先级：P0。当前状态：已做核心场景验证，完整边界未全部验收。

- 主会话 A 中产生后台调用 B 时，B 不得把 A 的 pane 身份和名字替换掉。
- 合法 subagent 保留自己的身份和展示，不继承或覆盖父会话名。
- 用户真正新建或切换会话时，应显示新会话的名字，旧会话的迟到结果不能覆盖它。
- 内部辅助调用不作为普通用户会话混入列表；未知角色不能仅靠名字猜测，历史记录不批量删除。

验收：真实 Claude、Codex 的主会话启动、命名、后台调用、原生改名及合法新开会话形成可复核证据；规则级测试和真实 Provider 验证分别记录。

30 秒活动窗口、Codex 调用者标识、缓存及绑定代次属于实现手段，具体选择与限制放在[方案](../solutions/Provider优先的会话命名统一方案.md)和 Journal 的 D-004～D-006，不增加为独立产品需求，也不承诺尚未验证的边界。
