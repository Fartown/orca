# Goal 模式待决问题清单

来自 [40-评审结论](./40-评审结论-2026-08-15.md) 的四方向评审 + 事故复盘。
每条:**问题是什么** → **有哪些解法** → **我的建议**。已定的会标出结论。

分三类:A 机制取舍(需要产品判断)、B 架构改造(代价大,要判断值不值)、C 工程缺陷(没有取舍,只需排优先级)。

## A. 机制取舍

### A1. 反复「声称完成又被驳回」该怎么处理 · **已定:门禁负责说清哪里没做完,计数器不再当刀**

> 这条最初写成「假完成计数该累计还是连续」,是问错了问题。真正要问的是:
> **反复驳回意味着什么?** 下面是修正后的版本。

**问题**

现在的规则:agent 声称完成、验收没过,计数加一;满 3 次终结目标,判词写「连续 3 次声称完成但验收未通过」。
这个设计假设「反复声称完成」是 agent 的病态 —— 它迷路了,再跑也没用,所以早停。

**但实际造成循环的,绝大多数是我们自己**:

1. **驳回内容是空的或没用的。** 今天两次都是。而且在「验收输出保尾是假的」那条修掉之前,
   任何输出超过 8000 字的检查,回灌给 agent 的都是几百行通过用例的噪音、零句失败原因 —— 它无从下手,只能再声称一次。
2. **判据本身不可达或有歧义。** 它改完能改的,剩下的怎么努力也过不了。
3. **它是真迷路了。** 这才是原设计假设的情况,实际最少见。

**实况证据**(第 6 轮,13:34):Kimi 收到的驳回是

> 驳回原因:`orca-goal-judge ... 退出码 1`
> 命令输出:`验收裁判(codex)没有给出可解析的判词`
> 「这不是新任务。你的完成自查得出了错误结论。**把这当成你的验证太弱的证据,而不是检查有问题的证据。**」

裁判根本没跑起来(模型配置不可用),提示词却断言是它自己验证太弱。它拿不到任何可改的东西,
却被要求「去修上面那个失败」—— 除了再声称一次完成,它没有别的动作可做。**循环是被制造出来的。**

**顺带,同一段提示词里还有一句是假的**:「验收配置在这个工作区之外,所以改这里的文件不会改变它」——
判据文件其实与 agent 同用户可写。这句话既不真,又主动给出了寻找方向。

**解法**

核心转变:**这个计数器不该是断路器,应该是「反馈回路没在收敛」的探测器,出口是人而不是终止。**

| 方案 | 代价 |
|---|---|
| (a) 维持现状(累计满 3 次终结) | 系统性误杀长目标;门禁自己坏掉时会把责任写成 agent 的诚信问题 |
| (b) 只调阈值语义(累计改连续 / 按进展重置) | 在「松一点紧一点」之间挪,没有触及循环的成因 |
| (c) 改成三条:门禁失灵不计数 + 同批反复失败升级给人 + 提示词不再无条件归咎 agent | 实现稍多;但同时消掉误杀和「制造循环」两个来源 |

**已定:(c)**,拆成三件事:

1. **驳回内容没有可操作信息时不计数。** 裁判起不来、判词解析不了、输出为空 —— 这些说明**门禁自己坏了**,
   该做的是响亮提醒人。理由不只是「分类错误」:**门禁失灵时守卫已经没有判定能力了**,继续跑本身就是错的。
2. **同一批条目反复失败时升级给人,而不是判死。** 连续几轮挂同一条判据,是「它满足不了这条」的证据 ——
   可能判据不可达、有歧义,也可能环境缺东西。把判据和它的历次尝试一起摆出来,由人决定改判据、补环境还是收摊。
3. **改掉提示词里那句「是你验证太弱」。** 它是**无条件断言**,而门禁本身会坏 ——
   这句话在门禁失灵时会主动把 agent 推向「去自己身上找不存在的问题」。改成陈述事实(哪几条没过、证据是什么),
   并明确告诉它:**如果你认为是判据或环境的问题,直接说,这不算失败**。同时删掉那句关于「你改不了验收配置」的假话。

**那还需要「最多几次」这个阈值吗**:基本不需要了。出口从「终结」变成「叫人」之后,阈值不再是一把刀,
保留一个很宽的触发条件(如同一批条目连续挂 3 次就叫人)即可。

**与其它条目的关系**:这条和 [A3](#a3-声称受阻要不要付代价--待定) 是同一个结论 ——
**守卫遇到自己判不了的情况,出口应该是人,不是终止**。
[A4](#a4-多批验收串行门禁还是全跑汇总--已定串行) 定的串行门禁正好配套:每次只判一批,
失败信息聚焦,agent 更容易改对,循环也更不容易发生。

### A2. 裁判要不要强制只读沙箱 · **已定:不要**

代码保持默认不加沙箱。

**但有一件必须做的**:`cli/README.md` 现在写着「codex 走只读沙箱,裁判**在机制上**改不了任何文件」,这与代码不符
(默认不传,要限制得显式给)。**文档撒谎比没文档糟**,会改成如实描述。

**可选的零成本兜底**(不改默认行为):判定前后各拍一次工作区 tree SHA,不一致就作废该次判定并告警。
它对提示词型裁判(claude)同样成立 —— 那边本来就只能靠提示词约束。要不要加,你定。

### A3. 声称受阻要不要付代价 · **已定:两种都做,做成可选项**

**问题**
agent 除了写「完成」,还能写「受阻:某某原因」。现在连写两轮,守卫就终止目标,**期间不做任何核实**。
对比:说「完成」要过全部裁判;说「受阻」零成本直接下班。所以对一个想收工的 agent,**撒谎说受阻是全局最省事的路径**,
而你在面板上只能看到它自己写的那句理由,没有任何独立信息可以质疑。

**解法**

| 方案 | 代价 |
|---|---|
| (a) 维持现状 | 无成本;但这道口子一直敞着 |
| (b) 受阻也跑一次验收 | 全绿本身就证伪了「受阻」;代价是每次多花一次验收时间(裁判型验收可能几十分钟) |
| (c) 受阻不终结目标,转「等你确认」态 + 通知 | 不花额外时间;由人决定继续还是收摊。代价是无人值守时目标会挂着 |

**已定:(b) 和 (c) 都实现,做成可选项由用户指定**(如 `--on-blocked verify|ask`),默认 (c)。

真受阻的场景(缺权限、缺凭证、需求有歧义)本来就必须人介入,所以默认走 (c);
但无人值守、且验收本身很快的场景下,(b) 更合适 —— 全绿本身就证伪了「受阻」。这两种诉求不必二选一。

这和 [A1](#a1-反复声称完成又被驳回该怎么处理--已定门禁负责说清哪里没做完计数器不再当刀) 是同一个结论:
**守卫遇到自己判不了的情况,出口应该是人,不是终止**。两条建议一起做才自洽 ——
否则「受阻」被引导去叫人、而「反复驳回」仍然自动判死,agent 会学会用前者规避后者。

### A4. 多批验收:串行门禁还是全跑汇总 · **已定:串行**

保持第一条失败就短路。

**配套要做的**:现在完全没说明这件事 —— 拆成四批后**只有第 1 批会被判**,后三批在它通过前永远不跑。
会在启动横幅和面板上写明。另外加 `--check-all` 开关,想看全景时手动跑一次全量。

### A5. 篡改扫描发现「验收被改松」之后该怎么办 · **已定:改成把证据交给能判断的人**

> 这条原来问的是「一次回复就放行,还是要拿证据消解」。两个选项都是错的,原因见下。

**问题**

守卫每轮扫「有没有把验收改松」的痕迹:删断言、给测试加 skip、改门禁配置、改 ignore 规则。
扫到 + agent 声称完成 + 验收通过 → 挡一轮,注入质证提示词。**但挡完这一轮,所有发现就被永久标记成「已确认」**,
agent 随便回一句、一个字节不改再声称一次就通过 —— 质证上限在最常见的模式下永远触发不了。
提示词模板还直接写着「这次即使你什么都没改也会采信」,等于把绕过方式发给被判定者。

**但真正的问题比这个更根本:扫描器假设了改动机是坏的。**

断言、测试、门禁配置、ignore 规则**本身就可能是错的**。人来改的话,发现某条断言写错了,**就是会直接删掉它** ——
这是正当修复,不是作弊。而静态规则区分不了「为了蒙混而改松」和「因为它本来就错而改掉」,
因为差别不在改动本身,**在于有没有正当理由**。

这也否掉了我原先的建议(确定性发现要求「把上一轮门禁定义还原后重跑」):
**如果那条门禁本来就是错的,这个方案会强迫 agent 去满足一条错误的规则,比现状还糟。**

**解法**

核心转变:**扫描器的职责是让改动可见,不是替人下判决。** 能判断"理由正不正当"的只有裁判或人。

| 方案 | 代价 |
|---|---|
| (a) 维持现状(一次回复即永久放行) | 质证只是提醒,不是闸门;而且默认 agent 有错 |
| (b) 机械规则:还原旧门禁重跑 | 门禁本身错的时候会逼 agent 满足错误规则 —— 比现状更糟 |
| (c) 把改动的 diff 交给裁判裁决,发现始终记录,模式性的升级给人 | 实现稍多;裁判要多读一段上下文 |

**已定:(c)**,三件事:

1. **发现照常记录**,进逐轮日志和面板 —— 「第 7 轮它把门禁改松了」这件事人要能看见,这是扫描器的主要价值。
2. **把具体的 diff 放进裁判的提示词**,让它在判定时一并裁决:「本轮验收定义发生了这些改动,
   请按**原始意图**判断目标是否仍然达成」。裁判本来就在读代码,多这一段上下文成本很低。
3. **不自动挡、不自动终结**;反复削弱这种**模式**升级给人。

**与其它条目的关系**:和 [A1](#a1-反复声称完成又被驳回该怎么处理--已定门禁负责说清哪里没做完计数器不再当刀)、[A3](#a3-声称受阻要不要付代价--已定两种都做做成可选项)
是同一个结论 —— **守卫判不了的事,出口是人(或裁判),不是机械规则。**

### A6. 开工前跑一次基线验收 · **已定:不做**

原提案是 start 时先跑一次验收,识别「检查本来就绿 / 本来就红」。**不做**,理由:

这套守卫的主要用法是**裁判型验收**(拿另一个模型对着判据核对),不是单测脚本 —— 而对裁判型验收,
「开工前先判一次」既费时间(单条可能几十分钟)又没什么意义。真正有单测脚本、且脚本状态可疑的场景很少,
为它引入一条默认路径不划算。

它想解决的两个问题,分别由别处兜住:「本来就红」由 [A1](#a1-反复声称完成又被驳回该怎么处理--已定门禁负责说清哪里没做完计数器不再当刀)
的「同一批条目反复失败就升级给人」覆盖;「本来就绿」属于配置质量问题,提醒一句即可,不值得为它花一次验收。

## B. 架构改造

### B1. 把一轮拆成阶段机 · **已定:直接做**

**问题**
现在整轮包一个 try 做重试,但一轮里各阶段的代价差两个数量级:重新快照几乎免费,**重新验收要几十分钟**。
结果是落盘之后出错,重试会把四批裁判从头再跑一遍 —— 而判词其实已经落盘,完全可以复用。

**解法**

| 方案 | 代价 |
|---|---|
| (a) 维持现状 | 罕见路径上会白烧几十分钟 |
| (b) 三行级止血:验收结果按(轮次 + 树哈希)记进目标记录,重试时读回不重跑 | 小;但重试粒度仍然粗 |
| (c) 完整拆成阶段机,每阶段自带失败策略 | 约 150 行重构,动的正是今天出过两次事故的那段代码 |

**已定:直接做 (c)**。重构量比我估的小,而且它同时把 (b) 的收益带上 ——
阶段机里「验收」本来就是一个自带结果缓存的阶段,重试时读回已落盘的判词,不重跑。

### B2. 把「等这一轮结束」抽成纯状态机 · **建议现在就做**

**问题**
那 80 行有 5 种出口、4 个时间阈值、依赖真实时钟,**完全测不到**。今天两次事故都发生在它周围,
而新加的测试只能靠模块 mock 间接驱动、还得真 sleep;有两条测试退化成了断言源码文本(把 `continue` 换成 `break` 照样通过)。

**解法**:抽成 `推进一步(状态, 观察, 当前时刻) → {新状态, 判定}` 的纯函数,时钟和终端观察留在外面。

**建议:做**。约 1 小时,纯搬运。做完所有阈值可以喂事件序列直接测,零 mock 零等待,
还能删掉那两个假测试。它是三条架构项里唯一能立刻降低后续所有改动风险的。

### B3. 引入「这一次运行」的概念 · **已定:做止血 (a)**

**问题**
目标身份等于终端句柄,没有「这一次运行」的概念。后果:同一终端跑第二个目标时,**逐轮日志不截断**,
面板时间线会混进上一代的轮次;`forget` 只删目标记录,认领/日志/判词/锁全留下,状态目录只增不减。

**解法**

| 方案 | 代价 |
|---|---|
| (a) 止血:`start` 时把上一代逐轮日志改名归档 | 一行,立刻消掉时间线串代 |
| (b) 全套:引入运行 ID,所有派生文件按它命名,`forget` 连带清理 | 中等,要同时改 CLI 与插件的路径约定 |

**已定:(a)**。`start` 时把上一代逐轮日志改名归档,立刻消掉面板时间线串代。
(b) 的收益主要是磁盘卫生,以后再说。

## C. 工程缺陷

没有取舍,只需要排优先级。按严重度排。

### C1. `stop` 会杀掉毫不相干的进程 · 高

锁文件只在干净退出时删除。SIGKILL / 断电 / `forget` 之后都残留,重启后 PID 空间重排,残留 PID 极可能落到别的进程头上。
此时 `status` 报「驱动在跑」、`start`/`resume` 被拒、而 `stop` 会对那个无辜进程先 SIGTERM 再 SIGKILL。**已实测复现**。

**解法**:(a) 锁里已经记了启动时刻,拿它和进程实际启动时间交叉校验;(b) 核对进程命令行是否真是 orca-goal;(c) 两者都做。
**建议 (c)**,并且 `forget` 要连带删锁。

### C2. Linux 上开箱即坏 + Windows 多处 POSIX-only · 高

CLI 名默认取 `orca`,而上游明确 Linux 上叫 `orca-ide`(为避开 GNOME Orca 读屏软件)。
Windows 侧另有:worker 用登录 shell 起命令、裁判裸名 spawn(实际是 `.cmd` 垫片)、面板生成的是纯 POSIX 脚本。

**解法**:命令名从上游的同一份定义推导(而不是硬编码);Windows 分支分别处理。
**建议**:先修 Linux 命令名(一行,且现在是**开箱即坏**);Windows 支持单独排期。

### C3. 一轮 6 秒跑完 20 轮 · 高

注入时刻取在**发送之前**,落在这个窗口里的上一轮结束事件会被当成本轮结束;而循环没有最短轮次间隔。
git 工作区靠空转熔断兜住,**文件夹工作区拿不到指纹、熔断关闭,完全没有兜底**,会向终端连灌 21 次提示词。**已实测复现**。

**解法**:(a) 注入时刻改到发送**之后**取;(b) 加最短轮次间隔;(c) 两者都做。
**建议 (c)** —— (a) 治本但仍可能被极快的假结束绕过,(b) 是兜底。

### C4. 陈旧的 working 状态导致轮次永不结束 · 中

hook 状态卡在一小时前的 `working`、终端一字节没吐,仍判 busy → 卡死上限永远差一步 → 配「时长不限」即永久挂起。
代码注释断言「working 没有陈旧风险」,而它恰恰是最容易陈旧的一档(上一轮被打断、agent 崩了、结束事件没发出来)。**已实测复现**。

**解法**:working 也要过陈旧检查 —— 太旧就回落到看终端有没有实际输出。
**建议**:做,和 B2 一起(它就在那段代码里)。

### C5. 非 ASCII 路径下篡改扫描整体失效 · 中

git 默认转义非 ASCII 路径,导致中文名的测试文件被归到源码类(删断言完全看不见)、中文目录下的门禁配置正则不匹配。**已实测复现**。

**解法**:取文件列表时关掉 git 的路径转义(`-c core.quotePath=false`)。
**建议**:做,一行。

### C6. `resume` 不重置取证基线 · 中

停几天后接回,第一轮把这期间别人的提交全算成「本轮改动」→ 篡改扫描报「改了门禁配置」「删了断言」,
质证计数已到阈值时第一轮直接判受阻。另外 `--worktree` 在 resume 上是哑弹:只改验收目录,不改取证目录。

**解法**:resume 时把基线置空(第一轮重新取);把取证目录和验收目录合成同一个字段。
**建议**:做前者(小);后者是记录格式变更,和 B3 一起考虑。

### C7. 面板 heredoc 定界符会被验收标准撞开 · 中

生成的启动命令用 heredoc 写判据文件,标准里只要有一行恰好等于定界符,文件被截断,**后续内容变成 shell 命令**。**已实测复现**。

**解法**:(a) 定界符加随机后缀;(b) 生成前检测冲突并换一个。
**建议 (a)**,顺带 (b) 兜底。

### C8. 数值参数不校验 · 中

验收超时写成非数字或 0 → 静默变成 1 毫秒 → 每条验收刚起就被杀 → 完成声明永远被驳回 → 三次后判死。
而 0 在别处(轮数、时长)明确表示「不限」,用户预期正好相反。**已实测复现**。

**解法**:所有数值参数统一校验,非法值直接报错退出;明确 0 在各处的含义。
**建议**:做。

### C9. 相对路径 + 后台运行静默失败 · 中

父进程打印「已在后台启动」并退出 0,子进程在状态目录下解析相对配置路径失败即退,唯一线索埋在驱动日志里。
README 的示例就是这个写法。工作区参数同样从未做绝对化。**已实测复现**。

**解法**:所有路径参数在父进程里先绝对化再传给子进程。
**建议**:做。

### C10. 认领文件几个边界 · 中

路径若是目录 → 每轮必抛 → 10 分钟后判受阻;无大小上限 → 重定向进去的大文件被整份读入;
匹配在任意行且大小写不敏感 → 日志行 `Complete: 5 files changed` 会被当成完成声明。**已实测复现**。

**解法**:读之前先看类型和大小;完成声明只认行首且区分大小写。
**建议**:做。
