# 集成分支自动出包

## 背景、用户场景与来源

原始事实：用户要求“合并集成分支自动打包 mac 和 apk”，希望直接从 GitHub 下载，不依赖本机。
已确认：用户以“改吧”接受并行构建、同 SHA 成套发布到当前 fork 预发布页，先使用未公证 macOS 内测包。
外部平台：Fartown/orca；自动出包已通过 PR #10 合入，更新链路在 PR #11 验证。无拆分子需求或待确认的产品推断。

## 范围

- In Scope：集成分支自动构建、手动重跑、macOS Apple Silicon DMG/ZIP/更新清单、Android APK、fork 更新检查及 Android 应用内下载和安装确认。Intel 版自 2026-09-17 起不再出包（D-005）。
- Out of Scope：Apple 正式签名/公证、应用商店、稳定更新频道、Windows/Linux 出包、本机 App 替换。

## 需求与验收

### REQ-401 集成分支自动构建

- 当前状态：实现中。
- 业务规则：fork/integration 更新自动触发，macOS 与 Android 并行，支持手动重跑。
- 验收标准：集成分支更新产生同一次工作流下的 macOS 安装包与 APK，无需本机启动构建。

### REQ-402 同源完整预发布

- 当前状态：实现中。
- 业务规则：全部平台锁定同一 SHA；全部成功才发布到 Fartown/orca prerelease；不改上游正式发布与稳定更新频道。
- 验收标准：发布页记录 SHA、版本、构建链接、校验和；任一平台失败不得公开半套下载。

### REQ-403 内测安装边界

- 当前状态：实现中。
- 业务规则：macOS 标明未公证；APK 保持稳定签名，集成构建版本递增，非集成版本不变。
- 验收标准：无需本机 Apple 凭据；核验 APK 签名；不冒充正式签名包，不承诺覆盖不同签名的安装。

## 实现约束与未决问题

### REQ-404 Fork 更新源与桌面更新文件

- 当前状态：实现中。
- 业务规则：集成包默认检查 Fartown/orca 完整预发布；同源发布 ZIP 和 latest-mac.yml，复用原生更新器，不绕过签名。
- 验收标准：Apple Silicon 选择正确；发布附带 Intel 占位说明文件，2026-09-17 之前、仍要求 Intel 更新包的集成包照常识别发布完整并更新；网络失败不冒充最新版，不退回上游；签名不满足时不宣称能够自动安装。

### REQ-405 Android 应用内更新

- 当前状态：实现中。
- 业务规则：集成包启动/回到前台自动检查，关于页可手动检查；用户确认下载 APK 后，核验摘要、包名、版本和签名，再进入 Android 系统安装确认。iOS 不安装 APK。
- 验收标准：新构建 versionCode 递增；能显示检查、下载进度、失败和重试；未知来源授权返回后可继续；取消安装不显示安装成功。

### REQ-406 发布说明与更新提示列出本次合入

- 当前状态：已实现，合入后核对通过。`integration-35175801533-0231e645f69d` 的发布说明与 `build-info.json` 列出 #31；用户这台 Mac 更新到该版本后，检查到下一个集成包时，更新提示的说明为 #32 的 PR 标题。
- 业务规则：每个集成包的发布说明列出相比上一个已发布集成包新合入的内容，`build-info.json` 同步记录为 `changes`。PR 合并显示「#编号 PR 标题」，没有 PR 的直接提交（如同步上游）显示提交标题；只看集成分支的第一父提交，同步上游带进来的上游提交不逐条列出。桌面更新提示显示最新三条标题，其余显示为 +N；清单没有合入列表时保留原固定说明。
- 验收标准：发布页与 `build-info.json` 的条目和两次发布之间集成分支的第一父提交一致，并附上一个集成包与完整提交差异的链接；同一提交重跑时与再往前一个不同提交的集成包对比；找不到上一个集成包或无法对比时只列本次提交，不阻止发布；清单中的合入列表格式不对时忽略该列表，不影响检查和安装更新。
- 生效边界：更新提示的文案由已安装的版本生成。装着旧版时，新发布在更新提示里仍显示固定说明；装上含本需求的版本之后，后续更新才显示合入标题。发布页不受此限制。

### REQ-407 集成包使用常规预发布版本号

- 当前状态：已实现，合入后核对通过。#32 合入后第一个集成包为「Orca 1.4.197-preview.25」；用户这台 Mac 从 #31 的版本自动更新到 `1.4.197-preview.25`；另一台 Mac 已在 #31 的版本上。Android 集成包是否已更新未核对。
- 业务规则：集成包桌面版本号改为 `上游版本-preview.N`，N 为出包开始时已发布集成包的最大编号加一（编号从发布标题读出；2026-10-06 起旧构建会被清理，不能再用数量，见 REQ-408）、连续递增；发布标题改为「Orca 版本号」。发布前重新统计：期间已有其他集成包发布（编号被占用，或更新的构建已发布）时拒绝发布，不产生重复或倒退的版本号。上游版本号带预发布后缀时出包失败并说明原因。Android versionCode 仍按构建时间生成，versionName 沿用 `mobile/app.json`；本机 `pnpm build:mac` 的本地包仍用旧格式。
- 验收标准：electron-updater 把 `-preview.N` 判为高于现有 `-local.…` 版本并提供更新；上游版本号升级后 N 继续递增。旧客户端会拒绝新格式清单，所以出包切换必须等用户的桌面与 Android 集成包都更新到兼容版本之后再合入。

### REQ-408 发布页分层：构建发布只保留最近 10 个，另出整理版

- 当前状态：已实现，合入后核对通过。#46 合入后的 `preview.40` 删除 30 个旧构建及其 tag，剩 10 个；手动触发的整理版 `fork-v1.4.221-1` 为 Latest、不带安装包、链接 `preview.41`；应用内更新检查仍选中最新构建（见测试用例 TC-409）。
- 业务规则：每次推送集成分支仍发布一个构建发布（预发布，tag `integration-运行号-提交`），因为已安装的桌面和 Android 集成包只认这种发布找更新。发布成功后删除更早的构建发布及其 tag，只保留最近 10 个（含本次）；被整理版引用的构建发布不删。另设「整理版」：给人阅读的发布，非预发布、设为 Latest、tag 为 `fork-v上游版本-序号`，不带安装包，链接到对应的构建发布。同步上游的那次出包自动发布整理版；手动触发出包时可选择同时发布整理版。整理版覆盖自上一个整理版以来的全部改动；还没有整理版时，从最近一次同步上游合并起，且至少覆盖本次构建区间。
- 上游版本：取整理版区间内同步上游期间官方发布的最新正式版；区间内没有同步时沿用上一个整理版的版本；都没有时用 `package.json` 版本。上游 main 的 `package.json` 落后于官方发布（2026-10-06 时 main 为 1.4.214，官方已到 1.4.221），不能代表带进了哪些内容。
- 编号：清理后已发布数量会变小，预览版编号改为「现有最大编号加一」（REQ-407），否则版本号会倒退，已安装的集成包不再提示更新。
- 验收标准：出包后构建发布数量不超过 10 个加被整理版引用的；应用内更新（桌面、Android，含已安装的旧版本）仍能找到最新构建；整理版不出现在更新候选中；清理或整理版发布失败只在构建日志里告警，不影响本次构建发布。
- 生效边界：清理不可恢复，被删构建的安装包无法再下载；用户已确认保留 10 个（D-006）。

### REQ-409 发布说明按用户可见变化分组

- 当前状态：已实现，合入后核对通过。`preview.40` 的正文按功能分组、固定说明折叠，`build-info.json` 只列 #46（见测试用例 TC-410）。
- 业务规则：构建发布与整理版的正文先写「这一版变了什么」，只列功能、修复、性能这类用户可见改动，按 fork 功能归组（由提交或 PR 标题的 scope 对应到功能登记表）；测试、文档、CI、构建、重构、格式、杂项折叠为「工程改动 N 项」；签名、证书、安装与 Intel 占位说明折叠到文末；提交、构建链接、对比链接放在折叠的「构建信息」里。`build-info.json` 的合入列表只放用户可见改动，同步上游合为一条，使桌面更新提示显示有意义的标题。
- 验收标准：用真实历史预演，测试与文档类提交不出现在「这一版变了什么」中；没有用户可见改动时说明为「本次只有工程改动」；合入列表仍满足旧客户端的格式校验（条数、标题长度）。

### REQ-410 同步上游写清带进了什么

- 当前状态：已实现，合入后核对通过。整理版 `fork-v1.4.221-1` 写出「同步上游（期间官方发布 v1.4.221，5 个提交）」与官方链接（见测试用例 TC-411）。
- 业务规则：区间内有同步上游的合并时，说明写出两次同步之间上游官方发布的正式版范围（如「期间官方发布 v1.4.209 至 v1.4.220」）与上游提交数，附上游对比链接和每个官方 Release 的链接；上游新功能提交按领域摘录（每个领域最多 3 条、总数最多 20 条），因混有基础设施提交而折叠。官方发布按发布时间落在两次同步的上游提交时间之间来匹配，不显示上游 main 的 `package.json` 版本（它落后于官方发布）。取不到官方 Release 列表时只给提交数与对比链接，读不到同步的提交历史时只写「同步上游」与上游提交链接，都不阻止发布。
- 验收标准：以 `c986a8309f`（合入 1166 个上游提交）预演，说明显示「同步上游（期间官方发布 v1.4.209 至 v1.4.220，1166 个提交）」与官方 Release 链接，不再只是一行「Merge remote-tracking branch」。

### REQ-411 整理版的 AI 中文短版本

- 当前状态：已实现。单测与预演（用假客户端记录实际输入）通过；合入后在未配置 key 时，整理版按设计省略短版本（见测试用例 TC-412）。用户决定暂不测试真实调用，待配置 `ANTHROPIC_API_KEY` 后再核对。
- 业务规则：仓库配置了 `ANTHROPIC_API_KEY` 时，整理版开头由 Claude（`claude-opus-5-5`，开启服务端拒答回退）根据本期 fork 改动、PR 说明（ELI5 与 What Changed 两节）与上游官方发布说明（The short version 一节，最近 3 个版本）写一段中文「短版本」，直接发布，并在段首标注「由 AI 生成，未经人工审阅」（D-006）。未配置、调用失败、被拒答或回复不是要点列表时省略这一段，整理版照常发布。构建发布不调用 AI。
- 密钥边界：只有一个没有写权限的独立任务持有该密钥，它把短版本写成文件交给发布任务；有写权限的发布任务不接触任何密钥，也不安装依赖。
- 验收标准：有 key 时整理版含标注过的短版本；无 key 或接口出错时整理版内容完整、出包不失败。

### REQ-412 改动经 PR 进入集成分支

- 当前状态：已实现。约定由 #47 写入 AGENTS.md 与 `docs/reference/fork-maintenance.md`（这两份文件不在本功能的改动范围内，故单独提交）；发布说明用 PR 编号区分 PR 与直接提交（见测试用例 TC-413）。
- 业务规则：除 `pnpm sync:upstream` 的同步合并及其为让门禁通过而在同一次推送里的修复外，改动都以 PR 合入集成分支，使每条改动在发布说明中有一个面向用户的 PR 标题。写入 AGENTS.md 与 fork 维护文档。
- 验收标准：文档写明该约定；发布说明对「直接提交」与「PR」区分显示。

### 当前约束

- 复用 Electron/Expo 入口，macOS 只输出 Apple Silicon DMG 与 ZIP。Intel 构建机慢且会因临时网络故障失败，用户确认不需要 Intel 版（D-005）。
- APK 沿用 Expo 模板 debug 内测签名，固定指纹核验；集成构建根据构建时间生成递增 versionCode，非集成构建保持 mobile/app.json 原值。
- 旧包没有新更新入口，需要手动安装一次新包；之后通过应用内更新。
- 用户手机现有签名未知，覆盖安装兼容性需实机确认；Apple 正式签名升级不属本轮。
- 更新属于设备本地操作，不依赖 SSH/配对主机，不改变远程协议或工作区行为。
- REQ-408～REQ-412 全部在 GitHub Actions 的出包任务中运行，只读写 Fartown/orca 的 Release 与 tag；不改客户端的更新检查，本地使用与通过 SSH 连接远程工作区时行为相同，不涉及 SSH 主机或配对主机。
- macOS 旧 ad-hoc 包无法跨版本原生升级，需一次手动迁移；固定自签原生正反例及 arm64 完整 Orca 替换/原终端连续性已通过隔离验收，正式发布仍须验证。自签不代表 Apple Developer ID 或公证。按用户要求，不做 Intel 专项原生验收。
