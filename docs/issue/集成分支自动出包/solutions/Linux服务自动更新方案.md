# Linux 服务自动更新

对应 REQ-414。现有服务直接运行解包的 AppRun，缺少 AppImage 来源和 CLI 更新接管；网页普通检查按钮返回空 Promise。正式发布有更新清单并不足以完成应用内更新。

## 复用边界

1. 保留 electron-updater 的发布选择、下载、SHA512 校验及 AppImage 原路径替换，不另写下载器和安装器。
2. Linux `serve --supervise` 根据已有 AppImage 缓存来源记录或运行环境解析安装来源。将来源和 payload 目录传给服务子进程，并启用既有 handoff 与 IPC ready 消息；来源不明或普通直接启动仍拒绝自动安装。
3. 沿用现有服务监督器的停止、失败限制、替换候选记录和 exec 逻辑。旧子进程退出后检查新 AppImage 的实际版本，再重新执行新包；新 CLI 读取持久化 handoff，只有目标版本子进程报告 ready 才清除请求。未匹配版本、下载/安装失败和用户停止均不得记成功。
4. AppImage 的标准 `APPIMAGE_EXTRACT_AND_RUN=1` 支持没有 FUSE 的 Linux。缓存和租约沿用上游机制，不能删除活跃 daemon 的 payload。原安装位置的 AppImage 被覆盖，不生成安装备份。
5. 网页普通检查入口打开并检查现有服务器更新对话框；服务版本使用共享连接层已验证的状态，不另行重连，不建立第二套更新界面。
6. handoff 的目录身份复用 `isSameUserDataPath`，比较已存在的数据目录并核对固定文件名；handoff 文件首次写入前也支持目录符号链接。接缝只调用功能自有路径解析器，不放宽其他配置目录的边界。
7. 安装验收复用独立的 `verify-linux-service.mjs` 断言真实服务版本、受监督自动更新支持及标签、PTY、已有 provider session 和 daemon 保留。初始化未完成或状态不满足时继续等待，不根据缺失字段判为成功。

## 执行归属与兼容

所有安装路径、缓存、环境变量、handoff 和监听端口属于服务执行主机。浏览器或桌面客户端只调用既有 updater RPC；SSH 主机不能使用客户端本地的 AppImage 路径。客户端失联时沿用共享连接层的可达状态和重连处理。

macOS 保持原 ShipIt 接管；Windows、deb/rpm 和无来源进程维持原支持判断。旧客户端继续使用既有 RPC 字段。新客户端连接旧服务时保留明确的手动更新提示。

## 验收

TC-415 用真实包 A→B 覆盖检查、下载、安装、重启、版本核验和终端连续性；分别通过本地浏览器与 root sshd 的隔离主机执行。开发源测试不能替代真实安装包的 UI 和重启证据。首次部署新能力仍需要一次原位覆盖安装，以后再走应用内更新。

目录别名修复的构建和验证使用独立 HOME、配置、缓存、端口和显示器，清除宿主 ORCA 环境变量。生产运行实例不参与测试；修复通过独立 PR 供用户查看后再合入。
