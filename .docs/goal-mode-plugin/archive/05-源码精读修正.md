## A. 我之前写错的(01 需要更正)

### A1 ⚠️ token 计量口径:不是"总 token",是 `(Δinput − Δcached) + Δoutput`

```rust
// accounting.rs:331
pub(crate) fn goal_token_delta_for_usage(usage: &TokenUsage) -> i64 {
    usage.input_tokens
        .saturating_sub(usage.cached_input_tokens)
        .saturating_add(usage.output_tokens.max(0))
}
```
且是**先对每个字段求增量再套公式**(`accounting.rs:313`)。

测试佐证(`tests/accounting.rs:11`):基线 `(input 100, cached 10, output 30)`,
当前 `(120, 14, 42)` → `Δinput 20 − Δcached 4 + Δoutput 12 = 28`。

含义:
- **`cache_write_input_tokens` 完全不计**
- **`reasoning_output_tokens` 不单独加**(它已包含在 `output_tokens` 里)
- 缓存命中的输入不计费

> 我在 04 §5.1 写的 Claude 口径是 `input + output + cache_creation`,**与 Codex 不一致**。修正见 D1。

### A2 ⚠️ "每次替换目标换新 goal_id" —— 只对一条路径成立

- `replace_thread_goal`(`goals.rs:156`):新 `goal_id`,`tokens_used`/`time_used_seconds` **清零**。
  只在**当前无目标**时走这条(`api.rs:222`)。
- 用户编辑 objective 且已有目标 → 走 `update_thread_goal`(`api.rs:200`),
  **保留 goal_id、保留累计用量**。

测试佐证(`goal_extension_backend.rs:896` `..._external_set_active_resets_baseline...`):
创建目标后消耗 20 → 编辑 objective → 再消耗 10 → 最终 `tokens_used == 30`。
编辑目标**不清零**,而且基线被正确重置,所以既不丢账也不重复计。

### A3 `create_goal` 的替换条件是 `status = 'complete'`,不是"任意终态"

```sql
-- goals.rs:236  insert_thread_goal
ON CONFLICT(thread_id) DO UPDATE SET … WHERE thread_goals.status = 'complete'
```
虽然 `ThreadGoalStatus::is_terminal()` 包含 `BudgetLimited | Complete`
(`model/thread_goal.rs:41`),但**模型侧 `create_goal` 面对 budget_limited 目标依然会失败**,
错误文案是 "cannot create a new goal because this thread has an unfinished goal"
(`tool.rs:203`,测试 `:133` 断言了这句)。

## B. 我之前漏掉的关键行为

### B1 ⚠️ 目标创建**之前**的本轮消耗不计入

`create_goal` → `mark_current_turn_goal_active` → `reset_baseline_to_current()`
(`accounting.rs:160`)。

测试佐证(`:190` `create_goal_resets_baseline_before_turn_stop_accounting`):
turn 基线 `(100,10,30)` → 消耗到 `(120,14,42)`(28 tokens)→ **此时才创建目标** →
再消耗到 `(127,16,52)` → 最终 `tokens_used == 15`,那 28 **没有**被计入。

> 04 完全没有这条。修正见 D2。

### B2 ⚠️ `budget_limited` 后继续记账,`usage_limited` 后停止记账 —— 不对称

| 状态 | 后续用量 | 依据 |
|---|---|---|
| `budget_limited` | **继续累加** | 结算 mode `ActiveOnly` = `status IN ('active','budget_limited')`(`goals.rs:520`);测试 `:363` 断言超预算后 25 → 35 |
| `usage_limited` | **停止累加** | `stop_active_goal_for_turn` 结算后 `clear_active_goal()`;测试 `:497` 断言 usage-limited 后再消耗,`tokens_used` 仍是 23 |

设计意图:预算是"我们自己设的线",越线后本轮的真实花费仍要如实记账;
用量限流是"外部强制中断",之后的消耗不属于这个目标。

### B3 Plan 模式的 turn **完全不参与**(token 与时间都不计)

`start_turn` 传 `account_tokens = !matches!(mode, Plan)`(`accounting.rs:80`),
而 `progress_snapshot` 在 `!account_tokens` 时直接返回 `None`(`accounting.rs:199`)
—— 所以连**时间**也不计。
且 Plan turn 上的 usage-limit 请求不会停目标(测试 `:688`)。

### B4 空闲时间也计入 `time_used_seconds`

`account_idle_goal_progress`(`runtime.rs:505`)在没有活跃 turn 时按墙钟结算。
测试 `:1012` `thread_resume_rehydrates_active_goal_idle_accounting`:
resume 后单纯 sleep 1.1s,`time_used_seconds >= 1`。

**目标是"活着就在烧时间",不是"只在跑 turn 时烧"。**

### B5 墙钟结算不丢余数

```rust
// accounting.rs:398
fn mark_accounted(&mut self, accounted_seconds: i64) {
    self.last_accounted_at = self.last_accounted_at.checked_add(advance)…
}
```
基线是**前进已结算的秒数**,而不是重置为 `now`。
`time_delta_since_last_accounting` 用 `.as_secs()` 截断,余下的毫秒留在基线里累积。
`mark_active_goal` 只在 goal_id 变化时才 `reset_baseline`(`accounting.rs:415`)——
所以切换目标不会把旧目标的时间算到新目标头上。

### B6 并发工具结算只记一次

`progress_accounting_permit`(信号量 1)+ `progress_snapshot` / `mark_progress_accounted` 配对。
测试 `:300` `parallel_tool_finish_accounts_active_goal_progress_once`:
两个 `tool_finish` 并发 → 只产生**一个**事件,`tokens_used == 30`。

### B7 SQL 层的终态保护与"复活即回落"

```sql
-- goals.rs:292  update_thread_goal
status = CASE
    WHEN status = 'budget_limited' AND :new IN ('paused','blocked') THEN status   -- ① 终态保护
    WHEN :new = 'active' AND token_budget IS NOT NULL AND tokens_used >= token_budget
         THEN 'budget_limited'                                                     -- ② 复活即回落
    ELSE :new
END
```
- ① `budget_limited` 不会被 pause/blocked 覆盖
- ② **resume 一个已超预算的目标会立刻回到 `budget_limited`**,除非同一次调用同时抬高 `token_budget`
  (第一个分支用的是新传入的 budget 比较)

另外 `pause_active_thread_goal` 只作用于 `status='active'`;
`usage_limit_active_thread_goal` 可作用于 `active` 或 `budget_limited`(`goals.rs:449`)。

### B8 过期 turn 的停止请求被忽略

`stop_active_goal_for_turn` 先查 `turn_is_current_active_goal(turn_id)`,不匹配直接返回。
测试 `:725`:turn-1 结束、turn-2 开始后,对 turn-1 的 usage-limit 请求不影响当前目标。

### B9 工具返回体与"报账"指令

```jsonc
{ "goal": {…}, "remainingTokens": 12, "completionBudgetReport": "Goal achieved. Report final usage…" }
```
`completionBudgetReport` 只在 `update_goal(complete)` 且(有预算 或 耗时>0)时出现
(`tool.rs:491`),内容是一段**要模型把最终用量讲给用户听**的指令。
`update_goal(blocked)` 不带(测试 `:762` 断言为 null)。

### B10 objective 会被 trim,并回填 thread preview

`create_goal` 与 `set_thread_goal` 都 `trim()`;
若 thread 的 preview 为空,用 objective 填充(`tool.rs:439`,测试 `:1058` 断言)。

### B11 外部改目标前必须先冲刷在途计量

`set_thread_goal` / `clear_thread_goal` / fork 之前都调
`prepare_external_goal_mutation()`(`api.rs:185`),持 `goal_state_permit` 跨越整个读写窗口。
测试 `:844` 断言它会产出一条 `turn-1:external-goal-mutation` 结算事件。

## D. 对 04 实施方案的具体修正

### D1 ⚠️ token 计量口径改为对齐 Codex(可配置)

04 §5.1 原文:Claude 侧统计 `input + output + cache_creation`。**改为**:

| 口径 | Claude 字段 | Codex 字段 | 说明 |
|---|---|---|---|
| **`codex-parity`(默认)** | `input_tokens + output_tokens` | `total_token_usage` 里 `(input − cached) + output` | 与 Codex 完全一致。注意 Claude 的 `input_tokens` **本身就已排除**缓存命中部分,所以不需要再减 |
| `billable`(可选) | 上式 + `cache_creation_input_tokens` | 上式 + `cache_write_input_tokens` | 更贴近真实计费(cache write 按 1.25x 计价),但与 Codex 不一致 |

`state.usage.metric` 记录实际口径,`goal-status` 一并展示。
**默认选 `codex-parity`**:预算语义与 Codex 对齐,用户从 Codex 迁移过来时预算数值可直接复用。

### D2 ⚠️ 新增"基线"概念:目标创建前的消耗不计入

04 §3.3 的 `cursor/KEY.json` 增加字段:

```jsonc
{ "transcriptPath": "…", "byteOffset": 12345, "inode": 8812345,
  "baselineTokens": 27768,        // 新增:goal-start 时的累计用量快照
  "lastTotalTokens": 51234 }
```
- `goal-start` 时:若能定位 transcript,立即扫描一遍取当前累计值写入 `baselineTokens`;
  定位不到则置 `null`,由 hook 首轮补齐。
- 计量改为 `usage.tokens = lastTotalTokens − baselineTokens`(下限 0)。
- **objective 被 `goal-edit` 修改时不重置基线**(对齐 A2/B1:编辑保留累计用量)。

### D3 ⚠️ `goal-resume` 必须做"复活即回落"检查(对齐 B7)

04 §8.2 原文:`goal-resume` → `status = 'active'`。**改为**:

```
resume:
  若 tokenBudget != null 且 usage.tokens >= tokenBudget → 保持 budget_limited,提示"需要先提高预算"
  若 turns >= maxTurns 或 elapsed >= maxWallClockMs → 同上
  否则 → status = 'active';重置 streaks;lastStopAt = now
```
并允许 `goal-resume` 顺带抬高预算(读 `budget.json`),抬高后才真正复活。

### D4 新增:Plan 模式轮次排除(对齐 B3)

Claude 与 Codex 的 Stop hook 输入都带 `permission_mode`。
`permission_mode` 表明处于计划态时:**本轮不计 token、不计 turn、不做续跑判断,直接放行**。
`goal-decision.mjs` 在 S2 之后、S3 之前插入:

```
S2.5  input.permission_mode 属于计划态集合 → allow(plan-mode),不修改任何计数
```
具体取值集合待实测确认(Claude 侧 `plan`;Codex 侧待定),**取不到就当作非计划态**(fail-open 到正常路径)。

### D5 确认无需修改的三处

- **墙钟含空闲时间**(B4):04 用 `now - createdAt`,天然包含空闲,与 Codex 一致 ✅
- **并发只记一次**(B6):04 已有文件锁 + `lock-busy` 放行 ✅
- **超预算那一轮仍记全账**(B2 前半):04 §4.4 的 S3 在预算审计 S6 之前完成计量 ✅
  但需补一条:**判定 `budget_limited` 之后,后续轮次不再累加**(对齐 B2 后半的 usage_limited 语义,
  因为我们的 hook 一旦判 limited 就在 S1 放行,不再进入 S3)——这与 Codex 的 `budget_limited`
  行为**有意不同**,原因是我们是轮界触发,没有"轮内继续"的概念。已在 04 注明。
