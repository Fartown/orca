## 需求目标与层级

用户为 Orca 中已有的交互式 agent 会话设定一个持久目标。看门狗在 agent 停下来后继续推动该目标，以独立证据核对完成声明，并让用户能够查明进展、验收结果和停止原因。用户保留查看会话、插话和主动停止的能力。

| 层级              | 目标                                                                 | 完成尺度                                               |
| ----------------- | -------------------------------------------------------------------- | ------------------------------------------------------ |
| 总目标            | 持续推进用户原始目标，并给出可核实的进度与停因                       | 不能以一次模型“完成”回复或局部测试通过代替整个目标达成 |
| P0 基础闭环       | 工作区目标 → 已有会话续跑 → 认领 → 独立验收 → 完成/预算结束/等待用户 | 现有源码已形成主链路；具体运行验收仍需测试记录         |
| P1 可靠性与可用性 | 故障接回、终端改绑、证据落盘、参数配置、面板观测；减少错误停止       | 有实现，也有明确差距，见逐条需求                       |
| P2 扩展与边界     | Windows/SSH/WSL 完整支持、完整运行代际标识等                         | 当前不作为已完成能力宣传                               |

## 既有实现的用户流程

1. 用户在 Orca 打开工作区和 agent 会话，通过 CLI 指定目标、终端、验收及预算；或在 Goal 面板填表后复制生成的启动命令。
2. 驱动通过 Orca 公开 CLI 向该终端发送目标，等待本轮结束，收集文件变化并读取 agent 的完成/受阻认领。
3. 声称完成时执行验收；未通过则将具体失败反馈给下一轮。声称受阻达到阈值后等待用户，或先执行验收核实。
4. 用户通过 status/watch 或面板查看；可以 stop 保留记录、resume 接回，原终端关闭后可以 rebind。
5. 当前代码也可能因空转、反复验收失败或驱动重试耗尽终止；这些行为与最新目标的差距单独列出，不掩盖为“已实现自动恢复”。

## 需求清单

“已实现”仅指存在对应源码；“部分实现”表示代码不能满足完整目标；所有产品运行验收状态均为本次未执行。

### REQ-101

优先级：P0。

需求与验收：在已有交互式会话中持续推进完整目标。正常忙碌时等待，轮次结束后继续；用户切换工作区不应改变目标终端。

当前状态：已实现外部 CLI 驱动；终端判定依赖 hook/PTY，不能保证所有 TUI/agent 无误判。

### REQ-102

优先级：P0。

需求与验收：目标按工作区持久化，终端仅作为可更换的输入位置。同工作区不得并发运行两个驱动；关闭终端后仍能找到目标并接回。

当前状态：已实现工作区 key、锁、resume、rebind、旧 key 迁移；软链别名、PID 身份与完整运行代际仍有边界。

### REQ-103

优先级：P0。

需求与验收：完成/受阻声明只从指定认领文件读取，旧轮次或无效内容不应被采信。

当前状态：已实现格式、大小、mtime 检查；不是从终端扫字符串，也不是独立 agent 工具协议。

修订（2026-09-23，待评审）：认领文件是「看门狗读不懂回复」时代的替代通道。按 REQ-124，守卫每轮直接读取执行 agent 的回复，认领文件降为可选的快捷信号，不再是完成与受阻的唯一入口；「只采信本轮」的时效规则保留。

### REQ-104

优先级：P0。

需求与验收：配置验收时，完成必须有独立命令结果；失败反馈须保留可操作证据。未配置验收必须明确未经验证。

当前状态：已实现原地命令门禁与独立 claude/codex 裁判：选了裁判就一定产生一条独立验收命令——还有没带命令的验收项时走条目模式，一条都没有时对目标正文与验收说明整体判定；“未经验证”只在 judge 为 none 且没有任何验收命令时出现。异常分类、缓存范围仍有限制；判据质量仍需用户保证。

### REQ-105

优先级：P0。

需求与验收：提供轮数与累计时长预算，显式 0 表示不限；停止驱动期间不扣预算，验收耗时应计入。

当前状态：已实现默认 20 轮/180 分钟与 activeMs；验收不受剩余目标时长严格截断，预算结束不等于停止 agent 进程。

修订（2026-09-23，用户已确认）：守卫每轮复盘、心跳巡检和验收后复盘的耗时都计入时长预算，面板与逐轮日志里单独显示守卫用时。

### REQ-106

优先级：P0。

需求与验收：识别 agent 正在等用户时暂停注入；连续受阻后通知用户，并可在用户回应后继续。

当前状态：已实现 hook needs-user 与认领 ask/verify；无 hook 时不能可靠识别权限对话框；停因分类见 REQ-113。

修订（2026-09-23，待评审）：「等用户」不再等于「叫人」。执行 agent 提问或声称受阻时，先由守卫按 REQ-125 判断能否从现有资料解答或自行解决；只有确属非人不可才通知用户。权限对话框期间仍不注入，这一条不变。

### REQ-107

优先级：P1。

需求与验收：瞬时终端/磁盘/取证故障不能静默丢失目标；需保留异常原因、认领与验收结果，并能恢复。

当前状态：已实现重试、取证降级、判词落盘、crash guard 与 resume；并非完整持久阶段机，故障边界需回归。

### REQ-108

优先级：P1。

需求与验收：每轮用独立文件证据展示改动；验证方式被修改时可见并交裁判判断，不以改测试本身推定作弊。

当前状态：已实现 git tree/HEAD、差异扫描与 gate diff；非 git 无该证据，普通 check 不自动解释 diff；未实现所有旧稿的硬门槛。

### REQ-109

优先级：P1。

需求与验收：面板展示目标、预算、当前轮次、等待/中断、验收与逐轮摘要；数据过期可辨。旧版的“操作命令可复制”保留为兼容能力，不再作为管理 UI 的完成标准；新的交互闭环见 REQ-116～REQ-120。

当前状态：2026-09-06 由原生“目标”面板替代；内置插件 stablyai.orca-goal 已随同一改动移除，旧插件页签路由归一到新页签。面板展示目标、阶段、验收项与证据、轮次与活跃时长、最近操作收据；数据来源为宿主 `goals.*` RPC 的权威快照，轮询 5 秒。真实 App 验证见 journal 2026-09-06 记录。

### REQ-110

优先级：P1。

需求与验收：支持长目标配置、多个 check、后台运行及可读错误；路径在后台 cwd 改变后仍正确。

当前状态：已实现 JSON/整行注释/目标数组、CLI 优先与路径绝对化；resume 与 judge 数值校验、配置字段仍有不一致。

### REQ-111

优先级：P2。

需求与验收：平台与远端支持边界准确：执行机器负责验收/证据/进程，不将断联当退出。

当前状态：2026-09-16 已补入 SSH relay 和配对 orcad 的宿主服务/资源、远端生成与执行、独立验收、断联不可验证、远程 Markdown 查看及草稿路由隔离。SSH 运行验证见 [本轮记录](../tests/runs/2026-09-16-SSH执行主机.md)，TC-357～TC-361 覆盖。Windows/WSL 和异机 Linux 不作为本轮已验收能力。

### REQ-112

优先级：P1。

需求与验收：删除“连续无文件变化即终止”的空转熔断；正常只读调研、铺环境等过程应继续，直到可靠停因或预算触发。

当前状态：未实现。2026-08-21 最新提案已有明确意图；当前仍使用 maxStallRounds=3 并生成 stalled。

修订（2026-09-23）：2026-09-22 事故再次复现提案所述误判——第 11～14 轮 agent 侧 API 报错、终端写明原因，守卫按「连续 3 轮工作区无变化」判空转终结目标。用户确认「三轮没干出活，不应该查问题找原因吗，为什么是结束了」。本条纳入修订方案首个工作包，按原提案删除，不以「改为叫人」替代。另：用户 App 当前装有未合入的热修，把空转改成了停下叫人，不符合本条；用户决定不回退（2026-09-23），新实现落地时整体替换。

### REQ-113

优先级：P1。

需求与验收：在无认领的停止点，只在有明确依据时区分等待权限、崩溃和普通停止，避免把续跑文本打进权限框。

当前状态：未实现最新提案的 obs.tail/明确签名判断；现有 hook/PTY 等待不等于这一能力已完成。

修订（2026-09-23，待评审）：「为什么停下」改由守卫读取回复与终端画面后判断，并入 REQ-124；不在驱动里维护终端文本签名集合（AGENTS.md 要求读 agent 画面的规则必须基于录制的 transcript，此前没有这类材料）。「权限框期间不注入」仍由状态存储的 needs-user 信号保证。

### REQ-114

优先级：P1。

需求与验收：门禁无法判定不计为 agent 失败；同一批验收项反复不能收敛时，将证据升级给用户。

当前状态：部分实现。inconclusive 已独立计数；普通 falseClaims 仍累计 3 次终止，没有“同批失败项→等待用户”。

修订（2026-09-23，待评审）：反复验收不过不再按次数终结目标。守卫逐条对照验收文档给出差距与解法；只有差距确属非人不可（REQ-125）才升级给用户。

### REQ-115

优先级：P1。

需求与验收：目标状态、驱动存活、agent 活动和验收有效性分别表达；记录删除/归档行为准确可预期。

当前状态：部分实现。driverError/driverAlive 独立展示；多处仍只探测 PID，forget 仅删目标 JSON，未形成完整 runId/侧车清理。

## 本轮确认的目标管理需求

来源：2026-09-05 当前对话。用户先询问新建入口、全部 Goal、完成进度及停止/变更方式；在交互调整建议后确认推进，随后明确“先写方案”。因此产品方向作为本轮方案输入，代码实现与运行验证均未开始。具体接口、数据迁移和能力分期属于方案建议，不冒充已批准的实现决策。

### REQ-116

优先级：P0。

需求与验收：右侧“目标”面板始终提供“新建目标”，已有活动目标不能隐藏入口；会话标题栏提供“设置目标/查看目标”，进入同一表单或详情。表单明确目标、验收标准与执行会话，预算等放高级设置；“创建并开始”应真正发起操作并展示结果，不让用户复制 CLI 才能完成主流程。同工作区冲突在启动时明确反馈，不隐藏其他工作区的新建能力。

当前状态：已实现（WP2）。右侧“目标”面板常驻“新建目标”；会话标题栏有“设置目标/查看目标”；命令面板有“目标：新建/查看目标”。“创建并开始”经 `goals.create` 真正拉起驱动并回读收据；同工作区冲突返回 conflict 并保留输入。

### REQ-117

优先级：P0。

需求与验收：提供目标列表与可返回的详情，支持当前工作区和全部目标范围；每条目标可识别所属工作区、执行位置、当前状态及是否需要用户处理。用户可主动选择目标，不能被“自动选择全局第一条 active”替代。全部范围的执行端覆盖与失联范围必须可辨，缺失数据不能表现为空列表。

当前状态：已实现（WP2）。列表/详情/返回、当前工作区/全部范围、进行中/待处理/历史筛选与搜索；执行端首个交付只有本机，其余端不列出。旧版 CLI 目标以“CLI 目标”只读行列出并可显式导入（WP4）。

### REQ-118

优先级：P1。

需求与验收：详情优先展示当前状态、正在进行的阶段、验收项及证据、最新产物和会话入口；轮次、预算和逐轮日志作为辅助。区分 Agent 自报完成与独立验证通过；没有可核实的验收项时不编造完成百分比，已消耗轮次不得解释为需求完成度。

当前状态：已实现（WP2/WP4）。详情按“状态与阻塞 → 验收项与证据 → 会话 → 执行记录”排布；带命令的验收项映射 gate 结果，只有整体判词时不拆条目；定义版本变更后旧证据标记为“证据已过期”。轮次与预算分开显示，不用轮次表示完成度；只有整体判词时展示“整体验收”结论与判词原文，不拆条目、不生成逐项通过数。

### REQ-119

优先级：P0。

需求与验收：UI 区分“暂停续跑”“停止执行”“继续”。暂停不再发起下一轮，并明确当前轮是否仍在执行；停止同时请求中断当前轮，只有得到对应执行端的确认才显示停止完成。未支持或无法确认中断时明示结果，不把发送成功、驱动退出或断联当作工作已停止。继续保留已有目标、执行历史及累计消耗。

当前状态：已实现（WP3）。暂停只关闭下一次注入；停止在关闸后向在途轮次发送中断，驱动等到本轮结束证据才写 turnStopped=true，否则收据为 confirmation_pending 并如实显示“中断未确认”；继续沿用累计轮次与时长。驱动缺席时由宿主按缺席结算。

### REQ-120

优先级：P1。

需求与验收：支持编辑目标、验收和预算，更换执行会话，以及保留证据的归档。运行中变更先停止旧目标继续推进，确认当前轮结束或中断后再应用；保留变更历史，旧验收证据不得自动代表新目标已通过。归档不删除执行记录；打开会话、改绑和继续不得静默创建另一个会话或改变执行工作区。

当前状态：已实现（WP3）。编辑与换会话仅在续跑已暂停且当前轮未运行时受理；改正文/验收递增 specRevision 并写入版本记录，只改预算保留证据；换会话限同一工作区；归档只写标记且要求驱动已退出，无永久删除入口。

### REQ-121

优先级：P0。
