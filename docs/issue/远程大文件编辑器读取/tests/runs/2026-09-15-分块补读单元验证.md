## 3. 关键断言

- TC-705 之前的断言是「truncated 时拒绝」，本轮改为「truncated 时返回全文」，并新增 TC-706 覆盖旧主机。两条一起保证了行为的改变是有意的而不是把保护删掉了。
- TC-702 用 4 字节分块读全中文内容：任何逐块解码的实现都会在这里产生替换字符，因此它是「先拼字节再一次性解码」这条规则的反向对照。
- TC-703 同时断言读取次数，避免实现变成「读完全文再判断超限」。

## 3.1 TC-708 真机 UI 验证（2026-09-16 补）

用 `tests/e2e/helpers/paired-electron-client` 起了**真实的配对环境**：e2e 应用作为 `orca serve` runtime 主机，再启动**第二个真实 Electron 桌面客户端**配对上去，在客户端的文件浏览器里点开主机 worktree 内一个 614461 字节的文本文件。

| 观测项 | 结果 |
| --- | --- |
| 夹具大小 | 614461 字节（> 512 × 1024） |
| 配对环境 id | 每轮新建，见 `validation.log` |
| 「too large」横幅 | 断言 `toHaveCount(0)`，未出现 |
| 首行标记 `ORCA-FIRST-LINE-MARKER` | Monaco 查找 `1 of 1` |
| **末行标记** `ORCA-LAST-LINE-MARKER` | Monaco 查找 `1 of 1` |

末行标记是这条用例的关键：它只存在于文件最后一行，远在 512 KiB 之后，**只有整份文件进入缓冲区才可能命中**。

### 反向对照（证明用例非空跑）

把 `runtime-file-read-client.ts` 里的修复摘掉、重新构建后跑同一条用例，**在预期的那一行失败**：

```
await expect(page.getByText('too large to open in the editor')).toHaveCount(0)
```

失败截图 `evidence/00-before-fix-too-large-error.png` 里的文案是
`Remote file is too large to open in the editor (524289 bytes)`——与用户报告的数字逐字一致。随后还原修复重跑通过。

证据：`evidence/` 下 `00`（修复前）、`01`～`03`（修复后）四张截图、`TC-708-录屏.webm`、`validation.log`。
