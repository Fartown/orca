# 集成分支自动出包

## 背景、用户场景与来源

原始事实：用户要求“合并集成分支自动打包 mac 和 apk”，希望直接从 GitHub 下载，不依赖本机。
已确认：用户以“改吧”接受并行构建、同 SHA 成套发布到当前 fork 预发布页，先使用未公证 macOS 内测包。
外部平台：Fartown/orca；自动出包已通过 PR #10 合入，更新链路在 PR #11 验证。无拆分子需求或待确认的产品推断。

## 范围

- In Scope：集成分支自动构建、手动重跑、macOS Apple Silicon DMG/ZIP/更新清单、Android APK、fork 更新检查及 Android 应用内下载和安装确认。Intel 版自 2026-09-17 起不再出包（D-005）。
- Out of Scope：Apple 正式签名/公证、应用商店、稳定更新频道、Windows/Linux 出包、本机 App 替换。

## 需求与验收

### REQ-401 集成分支自动构建

- 当前状态：实现中。
- 业务规则：fork/integration 更新自动触发，macOS 与 Android 并行，支持手动重跑。
- 验收标准：集成分支更新产生同一次工作流下的 macOS 安装包与 APK，无需本机启动构建。

### REQ-402 同源完整预发布

- 当前状态：实现中。
- 业务规则：全部平台锁定同一 SHA；全部成功才发布到 Fartown/orca prerelease；不改上游正式发布与稳定更新频道。
- 验收标准：发布页记录 SHA、版本、构建链接、校验和；任一平台失败不得公开半套下载。

### REQ-403 内测安装边界

- 当前状态：实现中。
- 业务规则：macOS 标明未公证；APK 保持稳定签名，集成构建版本递增，非集成版本不变。
- 验收标准：无需本机 Apple 凭据；核验 APK 签名；不冒充正式签名包，不承诺覆盖不同签名的安装。

## 实现约束与未决问题

### REQ-404 Fork 更新源与桌面更新文件

- 当前状态：实现中。
- 业务规则：集成包默认检查 Fartown/orca 完整预发布；同源发布 ZIP 和 latest-mac.yml，复用原生更新器，不绕过签名。
- 验收标准：Apple Silicon 选择正确；发布附带 Intel 占位说明文件，2026-09-17 之前、仍要求 Intel 更新包的集成包照常识别发布完整并更新；网络失败不冒充最新版，不退回上游；签名不满足时不宣称能够自动安装。

### REQ-405 Android 应用内更新

- 当前状态：实现中。
- 业务规则：集成包启动/回到前台自动检查，关于页可手动检查；用户确认下载 APK 后，核验摘要、包名、版本和签名，再进入 Android 系统安装确认。iOS 不安装 APK。
- 验收标准：新构建 versionCode 递增；能显示检查、下载进度、失败和重试；未知来源授权返回后可继续；取消安装不显示安装成功。

### REQ-406 发布说明与更新提示列出本次合入

- 当前状态：已实现。单元测试、真实发布记录预演与合入后的真实发布核对通过：`integration-35175801533-0231e645f69d` 的发布说明与 `build-info.json` 列出 #31；桌面集成包已从 e6277cf40f83 更新到该版本。更新提示里显示合入标题，要等下一个集成包发布后核对。
- 业务规则：每个集成包的发布说明列出相比上一个已发布集成包新合入的内容，`build-info.json` 同步记录为 `changes`。PR 合并显示「#编号 PR 标题」，没有 PR 的直接提交（如同步上游）显示提交标题；只看集成分支的第一父提交，同步上游带进来的上游提交不逐条列出。桌面更新提示显示最新三条标题，其余显示为 +N；清单没有合入列表时保留原固定说明。
- 验收标准：发布页与 `build-info.json` 的条目和两次发布之间集成分支的第一父提交一致，并附上一个集成包与完整提交差异的链接；同一提交重跑时与再往前一个不同提交的集成包对比；找不到上一个集成包或无法对比时只列本次提交，不阻止发布；清单中的合入列表格式不对时忽略该列表，不影响检查和安装更新。
- 生效边界：更新提示的文案由已安装的版本生成。装着旧版时，新发布在更新提示里仍显示固定说明；装上含本需求的版本之后，后续更新才显示合入标题。发布页不受此限制。

### REQ-407 集成包使用常规预发布版本号

- 当前状态：已实现，单元测试与基于真实发布记录的预演通过；按 D-004 须用户确认桌面与 Android 集成包都已更新到兼容版本后再合入，合入后第一个 `-preview.N` 集成包的发布与桌面、Android 更新待核对。客户端兼容（同时识别旧的 `上游版本-local.构建时间.提交` 与新的 `上游版本-preview.N`、新格式标题为「Orca 版本号」）已随 REQ-406 合入。
- 业务规则：集成包桌面版本号改为 `上游版本-preview.N`，N 为出包开始时已发布集成包数量加一、连续递增；发布标题改为「Orca 版本号」。发布前重新统计：期间已有其他集成包发布（编号被占用，或更新的构建已发布）时拒绝发布，不产生重复或倒退的版本号。上游版本号带预发布后缀时出包失败并说明原因。Android versionCode 仍按构建时间生成，versionName 沿用 `mobile/app.json`；本机 `pnpm build:mac` 的本地包仍用旧格式。
- 验收标准：electron-updater 把 `-preview.N` 判为高于现有 `-local.…` 版本并提供更新；上游版本号升级后 N 继续递增。旧客户端会拒绝新格式清单，所以出包切换必须等用户的桌面与 Android 集成包都更新到兼容版本之后再合入。

### 当前约束

- 复用 Electron/Expo 入口，macOS 只输出 Apple Silicon DMG 与 ZIP。Intel 构建机慢且会因临时网络故障失败，用户确认不需要 Intel 版（D-005）。
- APK 沿用 Expo 模板 debug 内测签名，固定指纹核验；集成构建根据构建时间生成递增 versionCode，非集成构建保持 mobile/app.json 原值。
- 旧包没有新更新入口，需要手动安装一次新包；之后通过应用内更新。
- 用户手机现有签名未知，覆盖安装兼容性需实机确认；Apple 正式签名升级不属本轮。
- 更新属于设备本地操作，不依赖 SSH/配对主机，不改变远程协议或工作区行为。
- macOS 旧 ad-hoc 包无法跨版本原生升级，需一次手动迁移；固定自签原生正反例及 arm64 完整 Orca 替换/原终端连续性已通过隔离验收，正式发布仍须验证。自签不代表 Apple Developer ID 或公证。按用户要求，不做 Intel 专项原生验收。
