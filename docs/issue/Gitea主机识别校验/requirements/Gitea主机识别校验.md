# Gitea 主机识别校验

## 背景

Orca 按 git 远程地址判断仓库托管在哪个平台。GitHub、GitLab、Bitbucket、Azure DevOps 有各自的识别规则；剩下所有不认识的域名都兜底当成 Gitea，直接向 `{网页地址}/api/v1/repos/...` 发 Gitea PR 请求。

公司或团队自建的非 Gitea 代码平台因此被误判：工作区卡片查不到 PR，Checks 面板空白，「创建 PR」走 Gitea 流程必然失败；每次刷新还会向对方主机发一批注定失败的请求，配置了 `ORCA_GITEA_TOKEN` 时连令牌一起发过去。

这也是给自建平台写插件的前提：内置逻辑不再冒充，插件才能接手这类仓库。

## 需求

### REQ-2101 只把确认是 Gitea 的主机当 Gitea

当前状态：已实现

其他平台都不认领的远程主机，先不带凭据请求一次该主机的 Gitea 版本接口 `{API 地址}/version`。主机明确回答「不是 Gitea」时，仓库按不支持的托管平台处理：不显示 Gitea PR 状态，不向 Gitea PR 接口发请求，不提供 Gitea 创建 PR 流程。「明确回答」包括普通错误页（如 500 纯文本）、404、跳转后的登录页、没有 `version` 字段的 JSON。

探测和其他 Gitea API 请求一样，由执行评审查询的那台机器发出，本功能不改变查询在哪里执行：

- 本地场景：工作区在 Orca 所在机器上，读远程地址、探测、Gitea 请求都在本机。
- SSH 场景：Orca 默认由 SSH 主机上的 orcad 托管工作区，整次查询在 SSH 主机上执行，探测和 Gitea 请求从 SSH 主机出网。仍走直连 SSH 路由（`ssh:` 主机）的工作区，远程地址经 SSH 在主机上读取，探测和 Gitea 请求由 Orca 客户端发出。配对 runtime 与 orcad 托管相同，在 runtime 主机上执行。
- 验收：远程指向非 Gitea 主机的仓库，在本地和 SSH 工作区里都显示为无托管评审；对方主机只收到一次版本接口请求，没有 PR 接口请求。

### REQ-2102 无法确认时保持原行为

当前状态：已实现

以下情况仍按 Gitea 处理，与改动前完全一致：

- 网络失败、超时；
- 网关或限流类回答：408、429、502、503、504；
- 版本接口要求登录：401、403，开启了「必须登录才能浏览」的 Gitea 就是这样回答的。

显式设置了 `ORCA_GITEA_API_BASE_URL` 时，视为用户已声明使用 Gitea，不做探测。

- 本地场景与 SSH 场景规则相同，判断只取决于执行查询的机器能否从对方主机拿到明确回答；orcad 托管时那台机器是 SSH 主机，所以客户端能访问而 SSH 主机不能访问的平台，在 SSH 工作区里按「无法确认」处理。SSH 断开时，查询要么无法在 SSH 主机上执行（orcad 托管），要么读不到远程地址（直连 SSH），都走不到探测这一步。
- 验收：真 Gitea / Forgejo 主机在本地和 SSH 工作区里照常显示 PR 和检查状态；对方暂时不可达时，不会被判为非 Gitea。

### REQ-2103 探测不泄露凭据、不重复打扰主机

当前状态：已实现

- 探测请求不带 `ORCA_GITEA_TOKEN`。令牌只发给已确认的 Gitea 主机。
- 同一个 API 地址的并发探测合并为一次。
- 结果缓存在执行查询的进程内存里：确认是 Gitea 的结果在本次运行中一直有效；确认不是 Gitea 的结果 5 分钟后才会重新询问；无法确认的结果不缓存。
- 下一次询问由正常的评审刷新触发，不另设定时器，也不自行重试。
- 本地场景与 SSH 场景相同：缓存在执行查询的进程内存里（本机 Orca 主进程，或 SSH 主机、配对主机上的 orcad），不落盘，不写任何文件、端口或环境变量。`ORCA_GITEA_API_BASE_URL`、`ORCA_GITEA_TOKEN` 也从这个进程的环境读取。
- 验收：同一主机下多个仓库、多次刷新，对方主机在 5 分钟内最多收到一次版本接口请求；请求头里没有 Authorization。
