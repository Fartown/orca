# 更新弹框聚合改动说明方案

对应需求：REQ-417（Fartown/orca#161）。

## 1. 根因分析

1. **客户端只看最新单包增量**：`release-catalog.ts` 只读取最新一个 Release 的 `build-info.json`。当用户跨越多个版本（如 `preview.100 -> preview.102`）且最新一版仅含 `docs` / `test` 等工程提交时，最新单包 `changes` 为 `[]`，桌面 `UpdateCard` 直接退回英文固定签名说明，把中间版本（如 `preview.101` 的 #152）一并丢掉。
2. **纯工程版本缺少回退摘要**：当用户已装 `preview.101`、最新为纯工程提交的 `preview.102` 时，`build-info.json` 不含工程改动条目，客户端也未读取 Release 正文中的工程改动折叠段。
3. **手机端与远程服务器更新弹框未接入改动摘要**：
   - Android `IntegrationUpdateGate` 弹框与关于/设置更新入口未消费 `release` 的合入列表，也未向 `fetchIntegrationRelease` 传入本机 `versionCode`。
   - Web 与配对/SSH 远程服务器共用的 `RemoteServerUpdateDialog` 在 `inspectRemoteServerUpdate` / `runRemoteServerUpdate` 中丢弃了执行主机返回的 `status.changelog`，且直接打开弹框时 `refresh()` 未传检查参数导致被动跳过服务端 `updater.check`。

## 2. 设计方案

1. **发布清单可选工程回退字段（`release-notes.mjs`、`publish-release.mjs`）**：
   - `changes` 维持只放同步上游与用户可见改动，确保跨版本聚合时工程提交不挤占前排展示位。
   - 新增 `manifestEngineeringChanges`，在存在工程提交时向 `build-info.json` 写入可选字段 `engineeringChanges`（最多 100 条、每条 `<= 300` 字）。旧客户端忽略未知字段。
2. **跨版本聚合与历史正文提取（`integration-release-changes.ts`、`release-catalog.ts`）**：
   - `fetchIntegrationRelease(platform, fetcher, options)` 接收可选 `{ installedDesktopVersion, installedAndroidVersionCode }`。
   - 先读取并校验最新完整构建；若提供了已装版本且最新版本高于已装版本，按运行号从新到旧遍历后续候选（最多聚合 10 个版本）：
     - 桌面端先用 Release 标题中的 `preview.N` 或 tag 中的本地构建短 SHA 预判，到达或早于已装版本时立即停止，不发起多余的 `build-info.json` 请求；
     - Android 端读取候选清单比对 `androidVersionCode <= installedAndroidVersionCode` 即停止；
     - 中间历史清单读取失败时仅停止向前追溯，绝不阻塞最新版本的检查与安装。
   - 对历史尚未写入 `engineeringChanges` 的已发布版本，从已取回的 GitHub Release Markdown `body` 或 Atom `<content>` 折叠段 `<summary>工程改动…</summary>` 提取条目填充回退列表（零额外网络请求）。
   - `integrationChangeSummary` 优先展示聚合后的用户可见 `changes`；仅当整个待升级区间用户可见改动为空时，回退展示聚合后的 `engineeringChanges`。
3. **三端界面统一接入**：
   - **桌面端**：`pinIntegrationReleaseFeed` 传入 `app.getVersion()`，复用共享 `integrationChangeSummary`。
   - **Android 手机端**：`mobile-updates.ts` 传入 `native?.getVersionCode()`；`IntegrationUpdateGate` 在 `Alert.alert` 正文顶部拼入改动摘要并附带 `preview.N (sha12)`；`useIntegrationUpdateAction` 暴露 `summary` 供 `IntegrationUpdateRow` 与 `IntegrationSettingsUpdateSection` 展示。
   - **Web 与配对/SSH 服务器端**：`remote-server-update-coordinator.ts` 在 `RemoteServerUpdateEntry` 保留执行主机返回的 `status.changelog`；`RemoteServerUpdateDialog` 打开时调用 `refresh({})` 触发真实检查，并通过 `src/renderer/src/integration-builds/RemoteServerUpdateNotes.tsx` 渲染改动摘要与发行说明链接。

## 3. 机器归属与 SSH 边界

| 资源 / 动作                                    | 本地桌面客户端            | 本地 Web（连接本机 `orca serve`）           | 配对 / SSH 远程服务器（如客户端在 Mac，服务在 SSH 主机）                                                       | Android 手机端                                                    |
| ---------------------------------------------- | ------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 已装版本读取                                   | 本机 `app.getVersion()`   | 本机 `orca serve` 进程的 `app.getVersion()` | **SSH 远端执行主机** `orca serve` 的 `app.getVersion()`（绝不读客户端版本充当远端已装版本）                    | 手机本机原生模块 `OrcaAppUpdate.getVersionCode()`                 |
| GitHub Release / Atom / `build-info.json` 请求 | 本机主进程 `net.fetch`    | 本机 `orca serve` 主进程 `net.fetch`        | **SSH 远端执行主机**发起请求并计算 `status.changelog`                                                          | 手机本机 `fetch`                                                  |
| 本地文件、端口与环境变量                       | 本机应用包 `package.json` | 本机 `orca serve` 监听端口与 handoff 文件   | 远端安装包、缓存、handoff 文件均属 **SSH 执行主机**；客户端仅经既有 SSH 转发隧道调用 `runtimeEnvironments` RPC | 手机应用缓存目录 `integration-update/`，不接触任何配对或 SSH 主机 |
| SSH 断开或未连接表现                           | 不涉及                    | 不涉及                                      | 由共享连接层管理可达性；失联主机在 `getRuntimeStatus` 判为 `offline`，本功能不新增任何定时器、重连或重试       | 手机更新独立于配对/SSH 主机连接状态                               |
