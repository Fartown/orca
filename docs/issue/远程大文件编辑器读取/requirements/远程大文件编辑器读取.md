# 远程大文件编辑器读取

## 1. 背景与目标

在配对 runtime（`orca environment` 对端）上打开文件时，编辑器走 `files.read` 这条 RPC。它是**预览尺寸**的：主机侧超出预算就返回 `truncated: true`，客户端随即抛出

```
Remote file is too large to open in the editor (524289 bytes)
```

拒绝而不是显示截断内容是对的——截断内容一旦可编辑，保存就会把文件后半截抹掉。但拒绝本身不是终点：**同一台主机上已经有 `files.readChunk`**，下载功能一直在用它按 384 KiB 分块取整份文件。编辑器没有用它，仅此而已。

目标：`files.read` 报 `truncated` 时，改用 `files.readChunk` 把整份文件取回来交给编辑器；不新增任何 RPC 方法或字段，因此不触发混版协商问题。

## 2. 用户场景

用户通过一台 Orca 客户端连到配对 runtime 主机，在编辑器里打开主机上一个 600 KB 的日志或数据文件，期望正常看到全文并可编辑保存，而不是一条「文件太大」的错误。

## 3. 范围

### In Scope

- 配对 runtime 上编辑器读取路径（`readRuntimeFileContent`）在 `truncated` 时的补读。
- 新的文本上限，与另一条远程传输（SSH）的文本上限对齐。
- 对端主机过旧（没有 `files.readChunk`）时的可解释失败。
- 跨分块边界的多字节字符正确性。

### Out of Scope

- 主机侧 `files.read` 的预览预算本身（保持不变，它服务的是预览而不是编辑）。
- 二进制文件（`files.read` 先以 `binary_file` 拒绝，走既有的 `files.readPreview` 回退，本需求不改）。
- SSH 与本地路径的上限（各自已有，且都大于本需求设定的值）。
- 文档预览链路（属 `document-preview-size` 功能，其边界明确不含 paired RPC 预算）。
- 写回/保存路径。

## 4. 需求点

### REQ-701 truncated 的读取改由分块补全

- 目标级别：P0；当前状态：已实现（单测覆盖）。
- 描述：`files.read` 返回 `truncated: true` 时，不再抛错，而是以 `files.readChunk` 从 offset 0 起按 384 KiB 连续读取直到 `eof`，拼成完整内容返回。
- 业务规则：不新增 RPC 方法或参数；分块大小取下载路径同值，落在 `files.readChunk` 的 512 KiB 参数上限内。
- 验收标准：truncated 后编辑器拿到完整内容；`files.readChunk` 被调用且 offset 递增。

### REQ-702 跨分块的多字节字符不被破坏

- 目标级别：P0；当前状态：已实现（单测覆盖）。
- 描述：UTF-8 多字节字符可能横跨两个分块，必须先把全部字节拼好再一次性解码。
- 业务规则：禁止逐块 `TextDecoder.decode`。
- 验收标准：以 4 字节分块读取全中文内容，结果与原文逐字符相等。

### REQ-703 对端过旧时给出可执行的提示

- 目标级别：P0；当前状态：已实现（单测覆盖）。
- 描述：主机没有 `files.readChunk` 时（RPC 报 `method_not_found`），保留失败，但提示改为指出补救办法。
- 业务规则：文案在原有大小信息之后追加「Update the Orca server to open files this size.」；不静默回退到截断内容。
- 验收标准：`method_not_found` 时报错文案包含该句；不返回任何内容。

### REQ-704 设定上限并在超限时停止读取

- 目标级别：P0；当前状态：已实现（单测覆盖）。
- 描述：上限取 10 MiB，与 SSH 这条远程传输的文本上限一致（本地 IPC 为 50 MiB，不在本需求范围）。
- 业务规则：累计字节一旦超过上限立即停止继续请求分块并报错，不把整份文件先读完再判断。
- 验收标准：上限 1 KiB、文件 4 KiB 时抛出超限错误，且请求次数明显少于读完全文所需次数。
