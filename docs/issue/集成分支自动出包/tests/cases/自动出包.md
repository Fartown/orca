## TC-401 自动构建与来源

- 关联需求：REQ-401；模块：工作流；优先级：P0；类型：单元、云构建。
- 前置条件：fork 工作流可用；测试数据：一个完整 Git SHA。
- 步骤：运行共享 mobile web bundle packaging workflow contract，验证工作流触发器和依赖；提交构建分支 PR；合入 integration 后检查自动运行。
- 预期：共享任务清单包含 `fork-integration-build.yml macos`，并验证其构建 mobile web bundle 前安装移动端依赖；macOS arm64 与 Android 在身份任务后并行，不再构建 Intel 版；checkout SHA 一致；产物非空；手动运行同样可构建。

## TC-402 发布完整性与范围

- 关联需求：REQ-402；模块：发布；优先级：P0；类型：单元、GitHub 集成。
- 前置条件：拥有 fork 仓库权限；测试数据：齐套、缺包、空包和上传失败输入。
- 步骤：执行发布反例测试；检查真实成功构建发布页和下载清单。
- 预期：PR 和其他仓库/分支不能发布；缺包不创建 release；上传失败停留 draft；齐套后转 prerelease；SHA、版本和校验和可追溯；已公开产物不覆盖。

## TC-403 签名与兼容边界

- 关联需求：REQ-403；模块：打包；优先级：P0；类型：单元、打包验签。
- 前置条件：macOS 和 Android 构建工具可用；测试数据：原签名、变化签名、无签名输出。
- 步骤：执行签名反例；对 DMG 中 App 验签并运行对应架构 Node 入口；对 APK 执行 apksigner verify。
- 预期：继承原打包资源和校验 hooks；macOS 发布使用固定自签证书、未公证，重签前后元数据不变；PR 普通包可 ad-hoc，不获取生产密钥；发布缺签名证据、指纹/版本不匹配时停止；APK 唯一签名指纹匹配现有 Expo 模板；集成版本递增、非集成版本保持 app.json。

## TC-404 Fork 更新源与 ZIP 清单

- 关联需求：REQ-404；模块：发布和桌面检查；优先级：P0；类型：单元、隔离原生探针。
- 步骤：生成双 ZIP 的 latest-mac.yml；运行 `release-catalog.test.ts`、`integration-update-feed.test.ts` 与原 updater 回归；测试网络失败和未完整发布；隔离运行原生 Squirrel 更新。
- 预期：SHA、版本、架构与摘要一致；集成包只解析 fork；上游包行为不变；签名不匹配时拒绝安装，记录为安装阻塞而非成功。
- 网络反例：GitHub releases API返回403/429但公开Atom及完整清单可读时，应通过同仓库回退发现；Atom也失败、清单身份不符或所有候选缺包时不能假报最新版。回退须HEAD检查APK或双ZIP/YAML，不请求上游、不附客户端Token。
- 原生验收：最小 App 同证书 A→B 完成替换重启；错证书和篡改包被拒绝且 A 能启动。真实 Orca 另验检查、下载、原生 staging、退出替换、新 PID/目标版本与原终端恢复，不能以探针代替完整产品验收。

- Intel 停止出包后（D-005）：`latest-mac.yml` 只列 Apple Silicon ZIP，桌面检查只要求 Apple Silicon ZIP；发布仍上传 `orca-integration-macos-x64.zip` 占位说明（合法 ZIP，只含 README），2026-09-17 之前的集成包要求的四个文件都在，照常识别发布完整；清单与 SHA256SUMS 记录占位文件的大小和摘要。

## TC-405 Android 检查、下载和安装

- 关联需求：REQ-405；模块：移动端更新；优先级：P0；类型：控制器、渲染、原生编译、设备验收。
- 步骤：运行 `mobile/src/integration-builds/update-controller.test.ts`；渲染实际更新组件验证按钮/进度/错误/授权状态；构建 APK，检查版本、权限、FileProvider、模块及签名；设备安装两版同签名 APK 后，从旧包发现新包并通过系统确认覆盖。
- 预期：新版本才提示；下载及安装防重复；校验失败不调用安装器；未知来源授权返回可继续；取消安装不冒充成功；iOS 不提供 APK 更新。
- 边界：渲染替身不证明系统安装成功；设备未接入时单独标记最后一步未验证。

## TC-406 更新下载中断与断点续传

- 关联需求：REQ-405；模块：移动端更新下载；优先级：P0；类型：单元、真机。
- 前置条件：设备已装同签名旧版集成包；发布源可注入故障（连接中断、504、忽略 Range 的 200、发送后静止）。
- 步骤：触发下载并在传输中途注入故障；记录发布源收到的 `Range` 请求头与返回状态码、应用侧重试次数与缓存目录中半成品大小；分别覆盖同一发布续传、换发布、跨 App 重启、摘要失败四种起点。
- 预期：
  1. 连接中断后，下一次请求带 `Range: bytes=<已落盘字节>-`，发布源返回 206，续传完成且总字节与清单一致；
  2. 收到非 2xx（如 504）后丢弃半成品，下一次请求不带 `Range` 从 0 重下；
  3. 发布源忽略 `Range` 以 200 返回全量时同样从 0 重下，不把整包追加在旧字节之后；
  4. 连接静止超过 45 秒时当次尝试被取消，并按已落盘字节续传；
  5. 缓存半成品属于别的发布 tag、或大于清单字节数时被丢弃；
  6. 摘要校验失败后缓存被清空，下一轮从 0 下载，不会反复续在坏字节上；
  7. 4 次尝试仍失败时，错误文案给出最后一次的 HTTP 状态与尝试次数；4xx 不重试。
- 边界：真机用例依赖可注入故障的本地发布源；线上 504 的具体成因不在本用例范围。

## TC-407 发布说明、清单与更新提示列出本次合入

- 关联需求：REQ-406；模块：发布、桌面更新提示；优先级：P1；类型：单元、真实发布记录预演、发布后核对。
- 前置条件：fork 已有公开的集成包；测试数据：只含一个 PR 的合入、同步上游的合并提交（带进几十个上游提交）、两次发布之间既有同步又有直接修复提交、同一提交再次出包。
- 步骤：
  1. 运行 `integration-builds.test.mjs`、`release-catalog.test.ts`、`integration-update-feed.test.ts`。
  2. 用真实的 fork 发布列表和本地集成分支历史执行发布预演（创建、上传、编辑发布三步只记录不执行），查看生成的 `release-notes.md` 与 `build-info.json`。
  3. 按发布任务的检出方式（完整提交历史、不含文件内容）拉取 fork，执行发布脚本用到的 `merge-base` 与第一父提交日志。
  4. 合入后打开第一个新集成包的发布页和 `build-info.json`。
- 预期：
  1. PR 合并显示「#编号 PR 标题」，同步上游只显示合并提交标题一条，上游提交不逐条出现；条目从新到旧。
  2. 发布说明附上一个集成包和完整提交差异的链接；同一提交再次出包时跳过同提交的集成包，与再往前一个对比。
  3. 找不到上一个集成包、上一个包不在当前历史上或查询发布列表失败时只列本次提交，发布照常进行；查询失败不掩盖随后的发布身份检查失败。
  4. 更新提示标题：旧格式为「Orca Integration 提交前 12 位」，新格式为「Orca 版本号」；说明为最新三条标题以「 · 」连接，超过三条加「+剩余条数」；没有合入列表时显示原固定说明。
  5. 清单中合入列表不是数组、超过 100 条、编号非正整数、标题为空或超过 300 字符时，客户端按没有合入列表处理，清单其余校验与更新不受影响。
- 边界：更新提示文案由已安装的版本生成，旧版客户端仍显示固定说明；真实更新提示要等用户装上含本需求的版本、再发布下一个集成包后才能看到。

## TC-408 常规版本号：编号、发布复核与兼容

- 关联需求：REQ-407；模块：出包身份、发布、发布清单解析；优先级：P0；类型：单元、真实发布记录预演、发布后核对。
- 步骤：
  1. 运行 `release-catalog.test.ts` 与 `integration-update-feed.test.ts` 的版本号用例。
  2. 运行 `integration-builds.test.mjs` 的编号、发布复核与工作流接线用例。
  3. 用真实的 fork 发布列表统计编号，以该编号和少一的编号各运行一次发布脚本（写发布的三步只记录不执行），并用 electron-updater 的 semver 与 Orca 自己的版本比较，判断新版本是否高于最新已发布的旧格式版本。
  4. 合入后核对第一个 `-preview.N` 集成包的发布标题、`latest-mac.yml`、`build-info.json`，以及桌面与 Android 集成包能否发现并安装。
- 预期：
  1. 解析接受 `1.4.197-preview.12` 与提交匹配的 `上游版本-local.时间.提交`；拒绝 `-preview.0`、`-preview.01`、带提交后缀的 preview、与清单提交不符的 local 版本；桌面与 Android 共用同一解析。
  2. 编号只看已发布、非草稿、标签符合集成包格式的预发布，跨分页读取；版本为 `上游版本-preview.(现有最大编号+1)`，最大编号从发布标题「Orca 版本号」读出，与已发布数量取较大者（兼容编号前的旧发布）；上游版本带预发布后缀、编号非法时失败。
  3. 发布时编号与重新统计的结果不符，或已有更新的构建发布时拒绝，且不创建、上传、编辑发布；旧格式版本或非法 Android versionCode 在任何 GitHub 调用之前被拒绝。
  4. 发布标题为「Orca 版本号」；身份任务带只读令牌统计发布，发布任务带上 Android versionCode。
  5. 两种版本比较都判定 `-preview.N` 高于 `-local.…`，上游版本号升级后仍递增，`preview.10` 高于 `preview.9`。
- 边界：出包切换合入前，须由用户确认桌面与 Android 集成包都已更新到含兼容逻辑的版本，否则旧客户端会报清单无效。2026-10-06 起旧构建发布会被自动清理（REQ-408），编号按最大编号递增，不受删除影响；但不能手动删除最新的构建发布，否则下一个会重复它的编号。

## TC-409 发布页分层：清理旧构建与整理版

- 关联需求：REQ-408；模块：发布、清理、整理版；优先级：P0；类型：单元、真实发布记录预演、发布后核对。
- 前置条件：fork 有 37 个构建发布（2026-10-06）；测试数据：14 个构建与一个引用其中之一的整理版、删除失败、已有同提交的整理版、上一个整理版不在当前历史上。
- 步骤：
  1. 运行 `release-lifecycle.test.mjs`。
  2. 运行 `.docs/integration-release-notes-review/2026-10-06/scripts/dry-run.mjs`：用保存的真实发布列表与本地历史预演 `c986a8309f`（同步上游）、`617f48da80`（PR 合入）、`617f48da80` 手动要求整理版三种出包，GitHub 写操作只记录。
  3. 合入后看第一次出包的发布页与构建日志；手动触发一次带 `milestone` 的出包；桌面与 Android 集成包检查更新。
- 预期：
  1. 本次构建发布之后，删除按运行号排在第 10 个之后、且没有被整理版正文引用的构建发布及其 tag；删除失败在日志里出 `::warning::`，发布照常成功。
  2. 有同步上游、或手动要求时发布整理版：非预发布、`--latest`、不带安装包，标题「Orca 集成版 上游版本 · 第 N 版」，正文链接到本次构建发布；同一提交已有整理版时不再发布；整理版发布失败只告警。
  3. 第一个整理版从最近一次同步上游合并起（预演 `617f48da80` 得到 `fork-v1.4.221-1`），之后从上一个整理版起；上游版本取期间官方发布的最新正式版（预演 `c986a8309f` 得到 `fork-v1.4.220-1`）。
  4. 已有更大编号的构建时，按较小编号出的包被判为过期，不产生倒退的版本号。
  5. 整理版的 tag 不符合构建格式，桌面与 Android 更新检查只看到构建发布。
- 边界：被删构建的安装包无法恢复。SSH 场景：更新检查始终在 Orca 客户端所在的机器上读取 GitHub，与是否连接 SSH 工作区无关；发布页改动不经过 SSH 主机，无需单独的 SSH 用例。

## TC-410 发布说明按用户可见变化分组

- 关联需求：REQ-409；模块：发布说明；优先级：P1；类型：单元、真实发布记录预演。
- 步骤：运行 `release-notes.test.mjs`；查看 TC-409 预演生成的 `release-notes.md` 与 `build-info.json`。
- 预期：
  1. PR 合并取说明首行作标题并带「(#编号)」；同步上游合并单独归入「同步上游」；其他合并不出现。
  2. `feat`/`fix`/`perf`/`revert` 与无前缀的提交按 scope 对应到登记表中的功能分组（`issues` 视为 Issues 看板），对应不上的归「其他」且排在最后；`test`/`docs`/`ci`/`build`/`chore`/`style`/`refactor` 折叠为「工程改动 N 项」。
  3. 没有用户可见改动时写「本次只有工程改动」，只有同步时写「见下方同步上游」。
  4. 安装、签名与校验，以及版本、提交、构建链接、对比链接都在折叠段里。
  5. `build-info.json` 的合入列表先放同步上游一条，再放用户可见改动；最多 100 条，每条不超过 300 字。

## TC-411 同步上游摘要

- 关联需求：REQ-410；模块：发布说明；优先级：P1；类型：单元、真实历史预演。
- 步骤：运行 `release-notes.test.mjs` 的同步上游用例；查看 TC-409 预演中 `c986a8309f` 的「同步上游」一节。
- 预期：
  1. 只匹配发布时间在两次同步的上游提交时间之间的官方正式版（不含预发布和其他 tag），按版本排序；预演显示「同步上游（期间官方发布 v1.4.209 至 v1.4.220，1166 个提交）」与各版本链接。
  2. 上游新功能提交按领域摘录、折叠，每组最多 3 条并显示总数。
  3. 读不到官方 Release 时只写提交数与对比链接；读不到同步的提交历史时只写「同步上游」与上游提交链接；都不阻止发布。

## TC-412 整理版 AI 短版本

- 关联需求：REQ-411；模块：摘要任务、整理版；优先级：P1；类型：单元、预演、发布后核对。
- 步骤：
  1. 运行 `release-notes.test.mjs` 与 `release-lifecycle.test.mjs` 的 AI 用例，以及工作流接线用例。
  2. 预演中用假客户端记录发给 Claude 的请求与输入（`.docs/integration-release-notes-review/2026-10-06/evidence/ai-summary-input/`）。
  3. 用户配置 `ANTHROPIC_API_KEY` 后手动触发一次带 `milestone` 的出包，查看整理版开头。
- 预期：
  1. 请求为 `claude-opus-5-5`、`fallbacks: "default"`、beta `server-side-fallback-2026-07-01`，不设 `thinking`；输入含 PR 的 ELI5 与 What Changed、官方 The short version。
  2. 回复为 2～12 行要点时写入整理版开头，并带「以下短版本由 AI 生成，未经人工审阅」；没有 key、拒答、回复不是要点列表、接口出错时省略，整理版与构建发布照常。
  3. 只有 `release-summary` 任务持有该密钥，它没有写权限，失败不阻止发布；发布任务不含任何密钥。
  4. SDK 来自根目录安装（`@anthropic-ai/claude-agent-sdk` 的 peer，`shamefullyHoist` 提升），上游移除它时守护用例失败。

## TC-413 改动经 PR 进入集成分支

- 步骤：检查 AGENTS.md 与 `docs/reference/fork-maintenance.md`；运行 `release-notes.test.mjs` 的分类用例。
- 预期：两份文档写明除同步上游及其修复外经 PR 合入；发布说明里 PR 带「(#编号)」，直接提交不带。
