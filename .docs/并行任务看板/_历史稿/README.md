## 贯穿始终、最终留下的判断

- 一件事的记录（Issue）和一次运行（会话）分开——来自 Multica
- agent **停下来** = 轮到我，不细分类型——来自你
- 信息在卡上，点了下钻；卡上不放动作，动作在会话里做——来自你
- 归档是**整理**（问题 / 结论 / 关键产物 / 未决与矛盾），不是存日志；随时发起，agent 办，我确认——来自你
- 只管 Orca 里的 agent、只管「需要我」这段；在 dashboard 上迭代——来自你
- **看板是全景不是收件箱**：一眼看到每一个任务在什么进展，而不是只看到欠我几件——来自你原话，v7 才被正确落实

## 被否掉的

- 让 agent 主动汇报介入点（v1）
- 四种介入的强分类与各自的必填字段（需求文档、v1、v2）
- 终端文本队列当看板（v1）
- 在产品未定时写数据结构与 hook 流程（v2）
- 卡片上的通过 / 驳回 / 回复按钮（v2）
- 收件箱/出队模型：完成型"看过即出队"会让未验收的产出静默消失，"必须显式办完"又退化成永不清空的停止列表（v2–v6，v7 否决）
- 按等待时长动态排序：会把最没人管的东西永久钉在顶上（v3–v6，v7 否决）
- 归属靠"价值驱动"：价值在事后显现、决策在事前做，理性用户每次都跳过（v6，v7 改为自动建/自动归入）
