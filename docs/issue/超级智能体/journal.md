### D-012～D-016 第一版建在 PR #81 上

- 日期：2026-11-05
- 背景：用户给出 Fartown/orca#81（本地任务「任务为主的工作流」的方案 PR），要求结合它的需求先做一个分配、管理任务与会话、能感知的总管，并想好任务、会话怎么给总管提供接口，复用已有的。PR #81 已设计调度会话、`orca task propose` 提案、`orca task progress` 回写、轮次结束、需要你、待验收，并定下原则「人说了才开工」「完成由人定」「不轮询」。
- 最终决定：待用户确认。推荐如下（详见 [总管第一版接口方案](solutions/总管第一版接口方案.md) §7）：
  - D-012：第一版总管就是 PR #81 的调度会话，常驻且唯一；任务是账本，不另起事项表。
  - D-013：唤醒用本功能的收件箱，语义照编排：只在空闲时、每个空闲期最多一次。
  - D-014：总管的写入一律走提案；`stop` 永远要确认。
  - D-015：第一版只做分配、管理、感知。
  - D-016：「只问」遇到要读代码的问题，提一份只读调查任务。
- 原因：
  - PR #81 让任务成为记录，正好是总管需要的事项。
  - 提案加用户确认，就是总管的审批。
  - 回写进展加轮次结束，就是总管的回执。
  - 复用这些，第一版只需补收件箱、唤醒、提案项类型和几条 CLI。
- 影响范围：总体方案的事项、唤醒、派工、回执在第一版由 PR #81 的对象承担；对 PR #81 提三处修改建议（Claude 调度会话以终端启动、对话标识按面板映射、提案项类型扩充）。

### D-011 要不要把 Claude / Codex 做成 subagent

- 日期：2026-11-04
- 背景：用户问把 Claude 或 Codex 做成 subagent 更好，还是不必、自己约束任务就行。核实两种 CLI 都支持无界面续接同一会话（`claude -p --resume <id> --output-format json`、`codex exec resume <id>`，Codex 另有 `--output-schema`）；Orca 已有续接参数（`src/shared/agent-resume-argv.ts`）和无界面运行（文本生成、自动化无界面派发）。
- 最终决定：待用户确认。推荐第一项。
- 原因：
  - 可靠性来自内核约束（派工单、结构化结果、事实核对、事项与看门狗），与形态无关。
  - 总管内部的 subagent 有机器、阻塞、可见性、恢复四个问题。
  - 外部 subagent（形态 B）给出 subagent 的语义：一份输入、一条结构化结果、结束明确；空闲不占进程、不花额度；跑在正确的主机上；会话号可续接、可转交互。
  - 开发类任务保留交互式会话，是因为无界面运行不能当场请求权限，人也看不到过程。
- 影响范围：REQ-2319；方案 3.5（执行形态 A/B/C）、4.13、4.14、11（V-10）；走查 §8。

#### 备选项

- 不做总管内部 subagent；轻量只读问答用外部 subagent（无界面单轮续接），开发、调查、评审用交互式 worker；统一靠内核约束（推荐）
- 探查员也用常驻交互会话（上一版方案）
- 用总管 CLI 内部的 subagent 做轻量任务

### D-010 分工的线画在哪里，轻量任务用什么执行

- 日期：2026-11-04
- 背景：用户先要求总管既不能老是自己干、也不能芝麻小事都派；随后提出「总管就不该自己动手，只做任务分发」，并问轻量任务该开 subagent 还是新会话，以及怎样让 codex / claude 作为子任务执行器像 subagent 一样高效通信、不浪费 token、不出现状态与信息不匹配。上一版方案留了「探查」口子，让总管自己读文件和 git，边界不够干净。
- 最终决定：待用户确认。推荐第一项（即用户提出的方向）。
- 原因：
  - 总管只碰控制面，判据清楚，能由权限配置强制，总管的上下文也保持干净。
  - 轻量任务用新会话而不用总管 CLI 的 subagent：subagent 够不着 SSH 主机上的仓库，前台运行时压住唤醒，不进编排、不挂事项、用户看不到，总管重启就丢。
  - 常驻、只读的探查员抵消新会话冷启动的开销。
  - 交接按派工单 + 结构化回执 + 内核核对，复用编排已有的 `worker_done` 契约与过期派工拒绝。
- 影响范围：REQ-2319、REQ-2320；方案 3.4 规则 14～16、3.5、4.12～4.14、5.1、5.3、10、11（V-9～V-12）；走查 §8。

#### 备选项

- 总管只碰控制面；轻量只读问题交给常驻探查员（新会话）；改东西、跑命令交给 worker；不用总管 CLI 的 subagent（推荐）
- 总管可以做限时限量的只读探查（读文件、`git log`），改东西才派 worker
- 轻量任务用总管 CLI 的 subagent

### D-007 总管会话用官方 CLI 的交互式终端，不经 Claude Agent SDK

- 日期：2026-11-04
- 背景：初稿让 Claude 总管走 Orca 的「结构化会话」，那条路径经 Claude Agent SDK 启动。用户指出这样无法使用官方订阅。核实 Anthropic 文档：未经事先批准，第三方开发者不能让基于 Agent SDK 的产品使用 claude.ai 登录或订阅额度，应改用 API Key；Claude Code 的法律与合规页说明 Pro/Max 额度按普通个人使用估算。同时确认 Orca 已有终端会话的聊天视图（桌面与手机），编排的终端道唤醒支持终端里的协调者。
- 最终决定：采用第一项。总管是官方 `claude` / `codex` 在总管工作区里的交互式终端会话，用用户自己的登录；桌面与手机用终端聊天视图显示；唤醒走编排终端道。第一期 Codex 也走终端会话，保持一条路径。
- 原因：这就是用户自己在用 Claude Code / Codex，订阅可用；Orca 不经手凭据；聊天视图与唤醒都已有。用量随唤醒次数增长，靠事件驱动、条件复查与合并压低；高频场景由用户在 CLI 里自行改用 API Key。
- 影响范围：REQ-2301；方案 §1、§2、§3.1～§3.3、§6、§10、§11（新增 R-6、V-5）；D-001、D-006 的表述。

#### 备选项

- 官方 CLI 的交互式终端会话 + 终端聊天视图（采纳）
- 维持 Claude 结构化会话（Agent SDK），要求用户为总管配置 API Key

### D-001 总管本体：智能体 CLI 会话，还是 Orca 内置的模型循环

- 日期：2026-11-04
- 背景：Muse、Dots、Cue 是厂商托管的智能体，自带模型调用、凭据与沙箱；DeepSeek Super-agent 和 agent-autoloop 则把现成的命令行智能体当作路由与执行者。Orca 目前不直接调用任何大模型 API，凭据都是各 CLI 自己的登录；结构化会话、手机聊天、编排唤醒都已围绕 CLI 会话建好。
- 最终决定：待用户确认。推荐第一项。
- 原因：复用 Claude Code / Codex 的能力、登录与用量；手机现在就能和它聊天；编排的协调者、唤醒、问答直接可用；Orca 不新增模型凭据与计费面。代价是总管的行为受所选 CLI 的上下文与压缩影响，用账本与记忆兜底。
- 影响范围：REQ-2301、REQ-2303；方案 §0、§3。

#### 备选项

- 总管是用户选定的官方智能体 CLI 的交互式会话，作为编排协调者（推荐；形态见 D-007）
- Orca 内置模型调用循环与工具调用，自管 API Key
