# REQ-1811 恢复后继续向原终端输入

关联 [Issue #127](https://github.com/Fartown/orca/issues/127)。优先级 P0；当前状态：已实现。

真实 Codex 在 App 重开后，下一条 Chat 的原文持久留存但未进入模型。#126 的 pre-submit provider guard 需要新 live hook，首次新 UserPromptSubmit 又必须先 Enter，形成循环。已提交请求的重启对账用例不能代替“重启后下一条新提交”。

固定执行主机、handle、PTY、完整 incarnation 和恢复物理归属可证明时，新客户端可以显式 opt-in 向原用户选择的 TUI 整体提交一次。物理连续性不等于当前 launch/provider 已证实；这类 receipt 必须标明 sessionUnverifiedAtSubmit。Enter 前只保存原 session 的文件边界，不能单凭旧行或正文确认。

只有执行主机在同一 PTY/incarnation 上获得 fresh provider 身份（原 session 相同）及 本次提交后的 turnStartedAt 和真实 hook transition，且原文件连续、真实 user 正文匹配，才确认。已知不同当前 session、旧 incarnation、replay-only、缺失完整物理归属均不能放行/确认。恢复后无需切 Terminal、手写第一条或新建进程；没有自动补发。

本地 App 重开、SSH managed/paired 主机重启、Git/文件夹工作区都需实测下一条新消息。旧客户端不 opt-in，保留原严格行为；新增参数/receipt 字段可选，不新增 stream opcode。原文保留、未知不重发、文件替换及同文争用保护继续成立。

当前 Chat 持续打开时，dispatching 通知抢先触发的对账不能因原请求仍 active 而被空操作吞掉；回执丢失后须在同 contact 内查询原请求，恢复正文确认，无需 reload。
