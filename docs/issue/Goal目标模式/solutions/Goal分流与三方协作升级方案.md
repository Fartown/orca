# Goal 开工对齐与守卫判断改进方案

## 0. 摘要

Goal 的设计是：用户把目标交给一个已有的 agent 会话，说一次就够，之后由驱动持续推进、守卫替用户判断和验收，直到真正做完。分工是“机制归驱动，判断归守卫，拍板归用户”。守卫相当于替用户坐在终端前的那个人，判断标准是“用户看到这个情况会怎么做”。

实际运行有两个问题。

第一，agent 发起不了 Goal。用户在聊天里说“用 Orca Goal 设个 goal 让 Codex 干、你来守卫”，agent 找不到入口，就自己拼一套来代替。五次这样的委托没有一次走到 Orca Goal。

第二，走到了也没完成。三次真实运行没有一次由守卫验收通过。原因有两层：

- 开工时目标没有真正对齐。用户一句话说不清目标，守卫补全后给出的是一张很长的清单，用户没看就开始了。
- 运行中守卫只要看到执行者在干活就等，不判断它干得对不对。

本方案做四件事：

1. **开工对齐**。守卫可以补全用户没说清的目标，由用户确认清单来把关，用户确认后才开跑。目标大的时候，一起确认分几批交付。
2. **agent 替用户发起**时走同样的对齐流程。
3. **守卫每次醒来先判断执行者做得对不对**，不对就马上纠正，对的才继续等。执行者停下来等评审时，由守卫替用户评审。
4. **确认框由守卫处理**。

不加规则、不加结局种类、不改驱动与守卫的分工。

## 1. 设计前提

以下是已经确认过、本方案不改动的内容，出处见修订方案 §2.4、§5.1。

- 驱动只管事实：这一轮结束没有、现在能不能发消息、预算用没用完。驱动不下结论。
- 守卫负责全部判断，一份提示词，四种结论：等一等、给指示、问用户、完成。
- 不用规则代替判断：不设“连续几轮没变化”之类的规则，每次唤醒都做完整判断。
- 只有三种结局：守卫验收通过、预算用完、用户停止。
- 预算是保险丝。发给执行者的消息和守卫的提示词里都不带预算。
- 验收清单只做开工对齐，不顶替目标原文。
- 尽量都由 agent 自己处理，只有非用户不可的事才问用户。

## 2. 证据

### 2.1 五次委托都没有走到 Orca Goal

10-26、11-10、11-11、11-19、11-20 五次，用户都是在聊天里让 Claude“开个 Codex 去做、你盯着”。`~/.orca-goal` 里没有这五天的任何记录。

11-19 那次，Claude 执行 `orca goal --help` 得到 “Unknown command”，`orca-cli` skill 里也没有 goal，约 4 分钟后改用 Codex 自带的 goal 功能，守卫由 Claude 自己用轮询脚本和问答文件拼出来。之后 15 小时，真实页面上一项都没修完。

### 2.2 三次真实运行都没有完成

| 目标                          | 结局             | 守卫结论                    |
| ----------------------------- | ---------------- | --------------------------- |
| 09-30 Markdown 还原 PC 端界面 | 180 分钟预算耗尽 | 等 13 次、问用户 3 次       |
| 10-23 复刻翻译插件            | 480 分钟预算耗尽 | 等 30 次、给指示 4 次       |
| 11-06 本地任务统一验收        | 人为停止         | 等 15 次、守卫调用失败 8 次 |

合计 73 次唤醒，58 次“等一等”，0 次“完成”。

**09-30 的经过。** 用户原话只有两句：“pc端你没有还原ui啊，好好对照看看，把ui给我还原”“主要是ui，先不要改交互和逻辑”。

- 生成的验收清单约 3600 字、18 条，包括设计系统、ZIP、版本、移动端不受影响、编译日志。用户没有回答清单里的任何问题就开始了。
- 清单“开工前请确认”第 4 条的默认做法是“先出方案，你确认后再动代码”。守卫按这条在 10:43 向用户提问“请评审方案”。用户 13:11 才回复“继续吧”。180 分钟里前 170 分钟没有改界面。守卫自己已经通读过那份方案，但没有替用户评审。
- 13:37 守卫发现执行者把桌面宽表的横向滚动改没了，笔记里写了“这算交互变化”，结论仍是“等一等”，并计划“下次看到它结束这一轮，就 instruct”。

**10-23 的经过。** 目标是复刻一个功能很多的翻译插件。清单 12 条，没有先后。执行者同时铺开五条子任务线，包括漫画修图和视频字幕。守卫每 15 分钟核实一次子任务确实在跑，然后继续等。8 小时后大半条目仍是“没做到”或“不确定”，没有任何一批功能被验完。

### 2.3 从代码和提示词核实的四点

- **执行者忙的时候，守卫的指示也能送达。** 驱动只在执行者停在确认框或终端断开时不发。但守卫的提示词没有告诉它这一点，所以它以为要等一轮结束。
- **守卫提示词的第 2 条是“执行者还在推进，就等”。** 它排在其他判断之前。执行者几乎总在推进，所以守卫几乎总在这一条就得出结论。
- **执行者停在确认框时，没有任何一方能处理。** 驱动检测到就不发消息；守卫看得到画面，但没有手段操作。10-24 03:00 一个子任务停在删除命令的确认框上，到 03:29 预算用完都没有人处理。
- **命令行启动不生成验收清单。** 只有面板流程会生成清单并让用户审阅。

## 3. 方案

### 3.1 开工对齐

用户一句话说不清目标是常态。所以对齐的办法不是限制守卫只能照抄用户的话，而是让守卫把目标补完整，并让用户的确认真正起作用。

**守卫补全目标，用户确认清单来把关。** 守卫可以补全用户没说清的地方，清单仍是原来的四节，用户直接审阅、确认清单即可。

**目标大的时候，一起确认交付顺序。** 守卫把清单分成几批，写明先交付哪一批。前一批做完并验过，才开下一批。这是解决“执行者越铺越大”的办法，验证结果见 4.1。

**默认做法必须能让工作继续。** “开工前请确认”每条都带“不回答就按……”，默认做法不能是“等用户确认后再做”。

**用户确认后才开跑。** 这是现有面板流程的规则，保持不变。

### 3.2 agent 替用户发起

用户在聊天里让 agent 发起 Goal 时，agent 直接发起，不让用户去面板。流程与面板一致：

1. agent 把用户的原话原样作为目标，选好执行会话和守卫。
2. 守卫生成清单。
3. agent 把清单发给用户确认。用户确认或修改后才开跑。
4. 开跑后，agent 只转述通知和结果，不自己另搞一套守卫，也不替执行者干活。

需要的改动：

- 给 orca CLI 加上 goal 的正式子命令，覆盖“生成清单、查看清单、确认并启动、查看状态、停止”。
- 在 `orca-cli` skill 里写明：把一件事交给另一个 agent 会话并要它推进到做完时，一律走这个入口；不许用执行者自带的 goal 功能、轮询脚本或问答文件代替；入口不可用时停下来告诉用户。

实施（2026-11-20）：

- 命令是 `orca goal draft`（`--terminal`、`--objective` 或 `--objective-file`、`--guard`）、`orca goal checklist <草稿> [--wait]`、`orca goal start <草稿> --terminal <终端> [--document <改过的清单>] [--max-turns] [--max-minutes]`、`orca goal status [<目标>] [--all]`、`orca goal stop <目标>`。它们调用面板用的同一组宿主方法（`goals.draftAcceptance`、`goals.getAcceptanceDraft`、`goals.create`、`goals.get`/`goals.list`、`goals.control`），不经过旧的直启命令。
- 守卫默认取与执行 agent 不同的一家，和面板一致。
- `start` 的目标原文和守卫取自草稿本身，用户改过清单就用 `--document` 传进来。草稿没生成好、或终端所在的工作区不是草稿的工作区时拒绝，要重新起草。服务端的 `goals.create` 不检查这一点，面板是在界面上拦的，所以 CLI 自己核对。
- SSH 工作区用全局参数 `--environment` 指向该主机上的 Orca Server。草稿、清单文件、目标记录和驱动都在主机上，CLI 只是发请求。
- `orca-cli` skill 的触发描述加上 goal、guard、“交给另一个 agent 做到做完”，正文加 Goals 一节。`orca agent-context` 由命令注册表自动生成，命令说明就是它的内容。

### 3.3 守卫先判断执行者做得对不对

现在守卫只要看到执行者在干活就等。改成：每次醒来先判断它现在做的事对不对，不对就马上纠正，对的才继续等。

把提示词现在的第 2 条换成下面两条：

> 2. 看执行 agent 现在做的事对不对，按三问：
>    - 范围：是目标要的吗？做了目标没要求的事，或改了目标说不要改的东西，算不对。
>    - 先后：是现在最该做的吗？清单里写了交付顺序的，按顺序来：前一批还没做完并验过，它却铺开了后面的批次，或在写目标没有要的方案、报告、取证材料，算不对。
>    - 验证：验证方式算数吗？用更容易的验证代替目标要求的验证，算不对。
>
>    有一问不对：instruct，写清停什么、先做什么、已经做的越界部分留还是撤。执行 agent 正忙时指示也能送达，不必等它这一轮结束。
>
> 3. 三问都对，并且它确实还在推进：wait。（后面沿用现有条文）

### 3.4 守卫替用户评审，和执行者来回确认

执行者停下来等评审、等确认，或请示怎么做时，不该直接问用户，也不该让执行者随便选一个做法。由守卫替用户把关：

- 守卫读执行者的方案或选项，对照目标给出结论：同意，或指出要改哪几点。
- 守卫拿不准时，让执行者补充备选做法和各自的取舍，下一次再定。
- 执行者不同意守卫的指示时，写明理由和证据，守卫下一次复核。

在提示词“执行 agent 说受阻、需要用户”那一条里加：

> 它停下来等评审、等确认，或请示怎么做：由你替用户把关。读它的方案或选项，对照目标给出结论——同意，或指出要改哪几点；拿不准就要它补充备选做法和各自的取舍，下一次再定。仓库规范里“先评审再编码”这类流程由你的评审满足，不是问用户的理由。

在发给执行者的规矩里加一句：不同意守卫的指示时，写明理由和证据，守卫会复核。

### 3.5 确认框由守卫处理

执行者停在确认框时，由守卫判断并处理：待确认的操作在目标范围内且不危险，就同意；否则拒绝，并指示执行者换一种做法。

做法：守卫的结论保持四种不变，在“给指示”时可以附带对当前确认框的处理（同意或拒绝）。驱动检测到执行者停在确认框、且守卫给了处理意见时，先按意见操作确认框，再发送指示。守卫没有给意见时，行为和现在一样。

各家执行者的确认框需要什么按键，实现前要各实测一次。

实施（2026-11-20）：

- 实测的画面与按键（Claude Code 2.1.329、codex-cli 0.171.0）：
  - Claude 的框是“Do you want to proceed?”，第一项“1. Yes”，页脚“Esc to cancel”。
  - codex 的框是“Would you like to …?”，第一项“1. Yes, proceed (y)”，页脚“Press enter to confirm or esc to cancel”。
  - 两家都是按 1 同意、按 Esc 拒绝。拒绝后 Claude 回到输入框，显示“Interrupted · What should Claude do instead?”；codex 显示“You canceled the request”。
  - 第一项不是 Yes 的框（例如目录信任框的第一项是“No, exit”）不认。
- 子 agent：Claude 后台子 agent 的确认框也出现在主终端，抬头写“from the general-purpose agent”，形式相同，按 1 一样能通过。这时主 agent 可能已经结束这一轮，状态行不一定是“等确认”。驱动认框看的是画面，不看状态行，所以守卫给了意见时照样能处理。
- 守卫结论多一个可选字段 `confirmBox`（approve / reject / 空），四种结论不变。reject 必须配 instruct，approve 只配 wait 或 instruct。
- 驱动做三件事：
  - 执行 agent 停在确认框或提问框上（状态行 `waiting`、`blocked`）时叫守卫，同一次等待只叫一次。原来这种情况不唤醒，只能等 15 分钟一次的定时巡检。
  - Claude 连着弹两个确认框时，状态行不变。同一次等待按“状态开始时间 + 画面上框的原文”区分，框换了就再叫守卫。这是实测中发现的：只按状态开始时间区分时，同意第一个框后第二个框没人管，一直等到定时巡检。
  - 叫守卫前先读一次画面，把认出的确认框原文作为材料交给守卫。SSH 主机上不一定有 `orca` 命令供守卫自己读屏。
  - 守卫给了意见时，先核对画面上还是同一个框，再按键，按完核对框已消失。
- 按完键后，驱动等状态行离开“等确认”再发指示。如果紧接着又弹出新的确认框，指示不发，等守卫看新框时再给。
- Claude 按 Esc 拒绝后不一定再发 hook。两次实测中，一次状态行很快离开了“等确认”，指示约 1 秒送达；另一次状态行一直停在“等确认”，指示没有发出去。所以改为：刚按掉确认框、并且画面上确认已经没有框时，这一次指示照发。

## 4. 验证

### 4.1 已做：历史记录重放

每次守卫唤醒的输入都有存档。取历史上的几个时刻，用原版和改版提示词各跑一次，对比结论。重放时守卫不能读终端和当时的文件，只凭当时的笔记、对话摘要和清单判断。每格只跑了一到两次，结果有随机性，只能说明方向。

**替用户评审（3.4）**

| 时刻                                | 当时结论 | 原版重放 | 改版重放                                                       |
| ----------------------------------- | -------- | -------- | -------------------------------------------------------------- |
| 09-30 第 2 次，执行者写完方案等评审 | 问用户   | 问用户   | 给指示：方案由守卫替用户评审通过，开始实施，不要再停下来等确认 |

**先判断做得对不对（3.3）**

| 时刻                                           | 当时结论 | 原版重放 | 改版重放                                                                             |
| ---------------------------------------------- | -------- | -------- | ------------------------------------------------------------------------------------ |
| 09-30 第 15 次，执行者改表格样式               | 等一等   | 等一等   | 两版措辞各跑一次：一次给指示（表格的滚动、换行逻辑和组件行为不要动），一次仍是等一等 |
| 10-23 第 2 次                                  | 等一等   | 等一等   | 给指示                                                                               |
| 10-23 第 25 次，执行者在深挖一个默认服务的细节 | 等一等   | 等一等   | 给指示：最多再查 5 分钟，查完就停，不要继续深挖                                      |

**交付顺序（3.1），针对“越铺越大”**

只改提示词时，10-23 第 20 次和第 30 次的结论都没有变化，还是“等一等”。在清单里加上分四批的交付顺序后再跑，每个时刻跑两次：

| 时刻                              | 只改提示词 | 清单里加交付顺序                                                                         |
| --------------------------------- | ---------- | ---------------------------------------------------------------------------------------- |
| 10-23 第 20 次，等 5 个后台子任务 | 等一等     | 两次都给指示：属于后面批次的子任务立即停掉，已写的代码留着；集中把第一批在真实界面里验完 |
| 10-23 第 30 次，等 4 个后台子任务 | 等一等     | 两次都是等一等                                                                           |
| 10-23 第 2 次，执行者在做第一批   | 给指示     | 一次等一等（判断它在做第一批，方向对），一次给指示                                       |

结论：

- 替用户评审和交付顺序这两项，重放里看到了想要的变化。
- 交付顺序在第 20 次起了作用，在第 30 次没有起作用，原因没有查清。
- 09-30 第 15 次的越界改动，一次抓到、一次没抓到，不稳定。
- 重放的输入输出保存在 `/tmp/goal-replay/`。

另外有一个没有预料到的现象：10-23 的三个时刻（第 7、9、10 次），原版提示词重放的结论就已经是“给指示”，而当时实际是“等一等”。当时的守卫是 Codex，重放用的是 Claude，重放时也不能用工具。守卫用哪个模型可能对“会不会只是等”有明显影响，这一点没有单独验证。

### 4.3 第 1 步实施后的复测（2026-11-20）

提示词按 3.1、3.3、3.4 改完后（清单生成按用户同日更正，不加“我的理解”、不分栏），用仓库里的提示词原文重新做了两项检查。证据在本机 `.docs/goal-prompt-review/2026-11-20/`（不入库）。

**守卫重放。** 把历史输入里的判断条文换成新的 `guard.md` 第 2～6 条，其余内容不动；每个时刻原版、改版各跑 3 次，守卫是 Claude，禁用全部工具。10-23 第 20、30 次的改版用带交付顺序的清单，并加一组“原版提示词 + 交付顺序清单”做对照。

## 5. 没有解决的问题

- **交付顺序不是每次都起作用。** 第 30 次重放里，执行者在做后面批次的功能，守卫仍然判断“方向和先后都对”。可能是当时的笔记已经把前面批次记成了基本完成，也可能是提示词还不够。需要看那一次的笔记原文再判断。
- **越界改动的识别不稳定。** 见 4.1、4.3。
- **清单字数超过 2000。** 见 4.3，两份都超出约两成；提示词里只写了上限，生成器不做校验（修订方案 C6），本次没有改。
- **大目标的清单生成可能超时。** 见 4.3。
- **codex 执行时没有在真机上出现过拒绝。** 按 Esc 拒绝只在 tmux 里对 codex 手动实测过。
- **拒绝后的指示送达只有单测覆盖。** 修复针对 Claude 拒绝后状态行停在“等确认”的情况，修复后的真机重跑没有再出现拒绝。
- **守卫对“没必要”的命令偏严。** 它会拒绝多余的只读核查；“危险”的判断则让位于目标原文，目标要求的强推、远程脚本都没有被拒绝。
- **守卫自己读屏依赖 `orca` 命令。** SSH 主机上不一定有，所以驱动把认出的确认框原文直接交给守卫。提问框等驱动认不出的画面，守卫在 SSH 上仍可能看不到。
- **agent 是否会按 skill 走到 `orca goal`，还没有在新会话里实测**（4.2 第 2 项）。
- **守卫模型的影响。** 见 4.1 末尾。如果确认 Codex 当守卫明显更容易只是等，需要调整默认的守卫选择，或者针对它单独调提示词。
- **守卫自身故障后的恢复。** 11-07 守卫连续失败，驱动在第 4 次失败后生成了通知，但两天多后才恢复。原因是守卫从 Orca 源码目录加载模块，当时源码里缺一个文件。这属于部署问题，不在本方案内。
